# プロンプト（モデルへ送る指示文）

このフォルダの `*.md` は、**実装がモデルへ送る指示文**です。文をここへ出しておくと、運用者が自分のモデル（12B / 27B / クラウド）に合わせて言い回しを調整でき、変更は PR の差分として追えます。

- 形式の契約: [implementation/v48-prompt-files.md](../implementation/v48-prompt-files.md) / 決定の記録: [ADR-0052](../docs/adr/0052-prompt-files.md)
- 書き方の見本: [`_example.md`](./_example.md)（`_` で始まるので読み込まれません）
- `_` で始まるファイル・`_` や `.` で始まるフォルダ・この README は読まれません。下書きは `_draft-xxx.md` にしておきます。

## ここに置くもの / 置かないもの

| 置く | 置かない |
|---|---|
| 実装が組み立ててモデルへ送る指示（system の規則・差し戻しの文・タスクの目的） | 人が編集して保存する成果物の雛形（エージェントの system プロンプト・Skill の文・ペルソナの基底文・回答の規律ブロック）。これらは利用者の資産で、保存後に画面で直せます |

**文はここ、組み立てはコード**という線引きです。どの節をどの順に使うか、条件で入れ替える規則、利用者のデータの隔離（`wrapUntrusted`）、JSON schema は今までどおりコードにあります。この形式には条件も繰り返しもありません（条件で変わる行は**節を分けて**、どちらを使うかはコードが決めます）。文字列でスキーマや制御構造を組み立てられるようにすると、隔離の規則までファイル側へ流れて検証できなくなるためです。

## ファイルの形式

```markdown
---
id: tool/calculate-expression
version: calculate-expression/v2
description: 関数電卓ノードの式を提案させる
---

## system
You write one expression for a calculator node.
Rules:
- Use only the columns listed in the user message.
{{extraRules}}

## repair
Your previous expression was rejected: {{reason}}
Return a corrected expression for the same intent.
```

- **frontmatter** は `---` で囲み、`id` / `version` / `description` の **3 キーだけ**を 1 行ずつ。YAML ではないので、引用符や複数行の書き方は使えません（`:` より後ろがそのまま値です）。
  - `id` は**このフォルダからの相対パスと同じ**（拡張子なし・`/` 区切り）。`factory/planner.md` なら `factory/planner`。ファイルを複製して id を直し忘れると、別名のつもりで元の文を上書きしてしまうため、一致しなければ読み込みません。
  - `version` は `名前/v番号`（`^[a-z0-9-]+/v[0-9]+$`）。**実行記録に残る版の文字列はこれが正**です。文の意味を変えたら番号を上げます（コード側に版の定数は置きません）。
  - `description` は日本語で「誰が・いつ・何のために」を 1〜2 行。一覧を眺めたときに、どこの文かが分かるように書きます。
- **節** は `## 名前` の行から次の `## ` まで。名前は `^[a-z][a-z0-9.-]*$`（`system` / `repair` / `rules.join` など）。同じ名前を 2 回書くと読み込みません。本文の前後の空行は落とされ、途中の空行は残ります。`###` 以下は本文の一部です。
- **差し込み** は `{{name}}`（`^[a-zA-Z][a-zA-Z0-9]*$`）。値は文字列・数値・文字列の配列（配列は改行で連結）。**埋めた値の中の `{{` は再解釈しません**（利用者のデータが差し込みの形をしていても、指示文を書き換えられません）。
- frontmatter と最初の `## ` の間に書いた文は誰にも届かないので、形式違反として弾きます。

### どの `{{}}` に何が入るか

各ファイルの `description` と、コード側の宣言（`export const XXX_PROMPT: PromptSpec = { id, sections }`）を対で読みます。`PromptSpec` はコードが実際に描画する節の一覧でもあるので、**そこに無い節は誰も送っていない死んだ文**です（同梱ファイルの検査テストが落とします）。値の意味は `render()` を呼んでいる箇所が持っています。

## 置き場所と上書き

1. このフォルダ（同梱）
2. `AGENTCONTEXT_PROMPTS_DIR` に指定したフォルダ（`;` または `:` 区切りで複数。Windows のドライブ接頭辞 `C:\` の `:` では切りません）

**同じ id は後に読んだものが勝ち**、置き換えは**ファイル単位**です。上書きファイルに書いた節だけが使われ、同梱の節が混ざることはありません（どの文が送られているか追えなくなるため）。上書きをやめたいときはファイルを消せば、次の呼び出しから同梱の文へ戻ります。

上書き用のファイルは、同梱のファイルをそのままコピーして文だけ直すのが確実です（`id` は同じままにします）。

## いつ反映されるか / いつ止まるか

- 文の編集は**再起動なしで反映**されます（次に使われるときに更新時刻とサイズを見て読み直します）。
- 実行中の再読込で**形式違反になったファイルは、直前の良い版が使われ続け**、警告がログに出ます（編集の途中で保存された半端なファイルで、動いているサーバーの指示が消えないようにするため）。
- **起動時**は、コードが要求する id と節が揃っているかを検査し、揃っていなければ**どのファイルの何が無いか・どう直すか**を出して起動を止めます。節を 1 つ欠いた上書きで、モデルの挙動が静かに変わる方が見つけにくく高くつくためです。
- ファイルを**足す**とき（新しい id の上書きを置くときを含む）は、起動時の検査を通す必要があるので再起動してください。

## 直し方が分からないとき

形式違反のメッセージは英語ですが、必ず「何が悪いか」と「どう直すか」を 1 文に含めています（ツールテンプレートの `invalid` と同じ流儀）。メッセージに出ているファイルのパスを開き、[`_example.md`](./_example.md) と見比べるのが最短です。
