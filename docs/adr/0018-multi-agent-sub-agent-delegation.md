# ADR-0018: マルチエージェントを「Agent集約へのサブエージェント参照 + ツール委譲実行」で実現する

- Status: Accepted
- Date: 2026-07-05
- Context doc: [docs/12-multi-agent.md](../12-multi-agent.md), [`ideas-v2.md` §13](../../ideas/ideas-v2.md)

## Context

`ideas-v2.md §13` で保留だったマルチエージェントの具体化が指示された。制約は2つ: **ユーザーがチャットする相手は1つのAgent**であること、**合成された関係を通常のAgentと同じように扱える抽象**にすること。

## Decision

1. **新エンティティを作らない。** Agent集約に第3の参照リスト `agents: AgentSubAgentRef[]`（`internalId` + `SemVer` + `usage` 委譲基準文）を追加する。サブエージェントを持つAgentも型・保存・バージョニング・実行入口のすべてで通常のAgentと同一。
2. **実行はツール委譲。** サブエージェントはルートのLLMに `ask_{publishName}` ツール（input: `{ message: string }`、description: `usage`）として提示し、呼ばれたら通常のAgent実行として入れ子で走らせ、最終応答（構造化出力があればJSON）をツール結果として返す。既存のTool Callingループに乗るため、実行エンジンの新設は不要。
3. **参照はSemVer固定 → 循環は構造的に不可能。** 保存済みバージョンしか参照できないため、バージョン参照グラフは構築時からDAG。追加の禁止則は同一 `internalId` への自己参照のみ。保存時に参照整合（サブの存在・`ask_` 名とTool公開名の衝突・自己参照）を検証する。
4. **Runツリー共有バジェットで暴走を防ぐ。** `maxDelegationDepth`（既定2・上限3）、合計model round（既定12）、合計tool call（既定16）をツリー全体で共有。per-Agentの既存上限（4 call / 5 round）は各ノードで維持。枯渇したサブは `error` で確定し、親へはエラーをツール結果として返す（親は応答を継続できる）。
5. **実効副作用は推移的に計算。** Agentの実効副作用 = 自Tool群 ∪ 全サブの実効副作用の最大。preview/test の read-only 制約は実効値で判定する。
6. **トレースは入れ子Run。** サブ実行は独立Runとして永続化し、親トレースに `agent_call`（childRunId付き）イベントを記録。Status画面の既存ドリルダウンで親→子→孫と追える（シナリオ検証のターン→Runリンクと同方式）。

## Consequences

- ✅ Chat・シナリオ検証・バージョニング・（将来の）MCP公開/エクスポートが**無変更でマルチエージェントに対応**する。均一抽象の直接の恩恵。
- ✅ `usage`（委譲基準）が明示・編集可能なテキストになり、Skillの発火条件と同じ方法論で検証・改善できる。
- ✅ LLMから見ると Tool もサブAgentも同じ「ツール」— 計算はTool・判断はサブAgentという設計指針を説明文で表現できる。
- ⚠️ 逐次委譲のみ（並列なし）。深い委譲はレイテンシが乗算的に増える — バジェットが実質の抑止。
- ⚠️ サブは各委譲で独立した `message` を受ける（会話状態の共有なし）。文脈の受け渡し品質はルートの要約力に依存する。改善が必要になったら「会話パススルー」オプションを別ADRで検討。
- ⚠️ `ask_` プレフィックスはTool公開名との衝突検証を保存時に行うが、後からToolが同名を取る競合は公開名管理（エイリアス/衝突管理）の一般問題として扱う。

## Alternatives considered

- **Team/Workflowエンティティの新設**: 「通常のAgentと同じ抽象」という要求に反し、Chat・検証・公開の各面で特別扱いが必要になる。却下。
- **サブ同士の自由対話（スウォーム）**: 停止性・コスト・観測の制御が難しく、ユーザー単一窓口の要求にも合わない。ツリー委譲で開始。
- **latest参照の許容**: 再現性を壊し、既存のSemVer固定方針（Tool/Skill）とも不整合。却下。
- **AgentRuntimePort（Mastra）のネットワーク機能へ委譲**: SDK固有機能への直結はSDK分離原則に反する。内部実装が成熟したらAdapterの最適化として再検討。
