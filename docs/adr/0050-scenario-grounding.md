# ADR-0050: 検証シナリオの前提は、データのプロファイルから決定的に合成して擬似ユーザーへ渡す

- Status: Accepted
- Date: 2026-09-20
- 関連: [implementation/v44](../../implementation/v44-scenario-grounding.md)（契約の正本）/ [ADR-0047](./0047-factory-lessons-from-estat.md)（e-Stat での実測。第6ラウンドの残課題）/ [ADR-0033](./0033-agent-factory-generation-loop.md)（生成・改善ループ）/ `docs/11-scenario-validation.md`

## 文脈

テンプレート経路（ADR-0049）で Tool は正しく作れるようになった。e-Stat の実測では、エージェントは正しい引数で Tool を呼び、計算済みの値を時点と単位つきで答えている。それでも `report.quality` は `below-targets` のままだった。

トランスクリプトを読むと、失敗しているのは検証する側だった。擬似ユーザー（12B）は「10月の総支給額 320,000円・165時間で時間当たり給与を算出して」と**自分で数値を作って渡し**、統計データしか持たないエージェントと噛み合わなかった。別の回では、データに無い「製造業の従業者数」を尋ねた。正しい回答（4,205.1065 円/時）を、自作の試算（450,000 ÷ 168）と比べて誤りだと言い張った回もある。

計画のシナリオ目標は妥当だった。擬似ユーザーに渡っているのは人物設定と目標の 1 行だけで、**相手が何のデータを持つエージェントなのかを、誰も教えていない**。検証の質が低いと、改善ループ（Analyst）は正しく動いているエージェントを「直そう」とする。ADR-0047 観測 2（盲目の Analyst が誤診する）と同じ構造が、1 つ手前の段で起きている。

## 決定

1. **検証の前提を `Scenario.context` へ決定的に合成する**。Stage 5 でシナリオを保存するとき、そのシナリオが使う Tool のデータソースのプロファイルから「検証の前提」ブロックを作り、計画の `context` の後ろへ付ける。中身は 4 点: 自分のデータは持たない（数値を作って渡さない）/ アシスタントが持つデータ（名前・行数・値の列・期間の範囲と粒度・カテゴリの例）/ 質問はその範囲内にする / データの値つきの回答を自作の試算と比べない。
2. **LLM に書かせない**。Planner に「context へデータの範囲を書け」と頼むのではなく、Factory がプロファイルの事実から組み立てる。見出しは `# Validation premises / 検証の前提 (factory-managed)`。
3. **ドメインは変えない**。`Scenario.context` は既存の項目で、擬似ユーザーの system prompt とアンケートの両方へ入る。利用者は Scenario 画面で前提を読めて、直せる。
4. **データの期間外の年を名指しするシナリオは、Planner へ 1 回だけ差し戻す**。既存の修復ラウンドに理由つきで乗せる。2 回目にも残っていたら計画は受理する（柔らかい違反。検証シナリオの言い回しで Run を落とさない）。
5. **ペルソナの `extraInstructions` は「ユーザーがどんな人か」だけ**と Planner に規則で伝える。エージェント向けの指示が入ると、擬似ユーザーがそれを自分の要求として繰り返す。

6. **アンケートの評点は向きを明示する**（Factory に限らず全シナリオ）。scale 設問の説明に「最小 = lowest / 最低、最大 = highest / 最高」を入れ、指示文に「数が大きいほど高評価。自由記述と評点を一致させる」と書く。実測では、自由記述で絶賛しながら評点 1 を付けていた。説明が `総合満足度 (integer 1..5)` だけで、どちらが良いのかをどこにも書いていなかった。
7. **答えが得られたら終える、を前提に含める**。前提ブロックの 5 つ目の項目として「目標に書かれた内容にデータの値で答えが得られたら達成とし、目標に無い追加の分析を求めて会話を延ばさない」を入れる。実測では、1 ターン目で答えを得た後も要因分析や別の比較を求め続けて `max-turns` になり、`goalAchieved: false` で終わっていた。

## 理由

- **決定的に分かることを確率的な推論に委ねない**（ADR-0047 を通した一貫した判断）。データの期間・カテゴリ・値の列は Stage 0 が既に全行から測っている。
- **検証する側の誤りは、作る側の誤りより高くつく**。Tool の欠陥は 1 本の Tool を壊すが、検証の欠陥は指標全体を歪め、改善ループを誤った方向へ回す。
- **見える場所に置く**。前提を擬似ユーザーの隠しプロンプトではなく `context` に置けば、利用者が「なぜこの質問をしたのか」を後から読める。

## 検討した代替案

- **Planner に前提を書かせる**: 12B は任意項目を埋めたり埋めなかったりする。書かれた範囲が実データと合う保証もない。
- **擬似ユーザーの基底プロンプト（ペルソナ側）に入れる**: ペルソナはシナリオをまたいで再利用される人物設定で、特定のデータに縛るものではない。データはシナリオの側の事情である。
- **範囲外の年を含むシナリオを決定的に書き換える**: 文章の書き換えは意味を変える。差し戻して直させ、直らなければ前提ブロックに任せる。
- **柔らかい違反でも Run を落とす**: 検証シナリオの言い回し 1 つで、生成に成功しうる Run を計画段階で失う。釣り合わない。
- **回答の数値がツール出力に含まれるかを決定的に照合して `goalAchieved` を裏取りする**: 効果は大きいが、指標の定義を増やす別の増分である（非スコープ）。

## 実測（前提ブロックを入れた直後。12B）

- 擬似ユーザーの質問は**すべてデータの範囲内**になった（「eStat 完全失業者の 2023年1月〜12月の月次推移と前年同月比」など）。架空の数値・対象外の指標は 0 件。ペルソナの `extraInstructions` も「ユーザーがどんな人か」だけになった。
- 前年同月比のパターンは目標達成率が 0.5 → 1.0。満足度だけが 1〜2 のままで、読むと自由記述は高評価だった → 決定 6。
- 時間当たり給与のパターンは、答えを得た後の深掘りで `max-turns` が続いた → 決定 7。
- e-Stat の `注記`（長文の断り書き）がカテゴリの例として前提に載り、無駄に長くなった → 値の最大長が 30 文字を超える列は例に出さない。

## 実測（決定 6・7 を入れた後。同じデータ・同じ 12B）

| パターン | 前（前提なし） | 前提ブロックのみ | 前提 + 評点の向き + 終了の規律 |
|---|---|---|---|
| 完全失業者の前年同月比 | 達成率 0.5 / 満足度 2.0 / `below-targets` | 1.0 / 2.0 / `below-targets` | **1.0 / 5.0 / `met-targets`**（1 周目で達成） |
| 時間当たり給与（2 ソースの比） | 0.5 / 2.5 / `below-targets` | 0.33 / 1.0 / `below-targets` | **1.0 / 4.0 / `met-targets`**（1 周目で達成） |

- 評点は自由記述と整合するようになった（絶賛 → 5、指摘あり → 2〜4）。
- 答えを得た時点で会話が終わるようになり、`max-turns` は 0 件。目標を 1 周目で満たすので改善ループが回らず、Run の所要時間は約 20 分 → 4〜6 分になった。
- 残る揺れ: 会話の `goalAchieved` は true なのにアンケートの `q1`（目的を達成できたか）が false の回が 1 件あった（評点は全て 5）。指標（`goalAchievedRate`）は会話側の値を使うので判定には影響しない。

## 結果・影響

- Factory が作るシナリオの `context` が長くなる（最大 1,800 文字程度）。擬似ユーザーの毎ターンの入力トークンが増える。
- 手で作ったシナリオには付かない（Factory の外では対象エージェントのデータを決定的に知る手段が無い）。
- Planner の修復ラウンドが、接地の違反でも 1 回使われることがある（モデル呼び出し +1）。
- 改善ループはシナリオを書き換えないので、前提ブロックは Run を通して変わらない。
