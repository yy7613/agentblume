# ADR-0037: LLM 判定の基準別採点・判定契約・自己一貫性

- Status: Accepted
- Date: 2026-09-13
- 関連: [docs/11-scenario-validation.md §9](../11-scenario-validation.md#9-llm-判定基準別採点判定契約自己一貫性) / [docs/04-api-spec.md §3.3](../04-api-spec.md#33-評価-実験と-judge-ルーブリックexperiments--judge-rubrics) / [ADR-0020](./0020-mastra-evals-agent-evaluation.md) / [ADR-0021](./0021-versioned-evaluation-assets.md)

## 文脈

実験（Experiment）の judge 指標は、ルーブリック（Judge Rubric）を system prompt に埋め、応答を `{ score: 0..1, reason }` の 1 点で返させていた（`src/adapters/evaluation/structured-judge-evaluator.ts`）。ルーブリックは基準（criteria）ごとの重みと段階（levels: 0 と 1 を含む 0..1 の離散値）を持つのに、判定者にはその構造を使わせず、合成は判定者任せだった。これには次の問題がある。

1. **不透明な単一スコア**。どの基準で減点されたかが分からず、実験比較で「何が退行したか」を追えない。判定者が段階を無視した中間値（0.73 など）を返しても検出できない。
2. **偏りの制御が無い**。LLM 判定者は長い・自信ありげ・体裁の整った応答を高く付けやすく（verbosity / authority bias）、結論を先に出すと理由が後付けになる。プロンプトはこれらに触れていなかった。
3. **判定者の更新が結果に痕跡を残さない**。プロンプト文面やルーブリック改版でスコアが動いても、レコードからは「エージェントが変わった」のか「判定者が変わった」のか切り分けられない。判定コスト（トークン）も記録していなかった。
4. **判定者が最終応答しか見ない**。ツール呼び出しの正しさや会話の流れへの適合は、応答文だけでは判定できない。
5. **1 回の判定は不安定**。温度 0 でも判定は揺れる。揺れの大きさが見えないので、スコア差が実力差なのか判定のばらつきなのか分からない。

参考: Autorubric（ルーブリック基準別の自動評価、arXiv:2603.00077）、CheckEval（チェックリスト型の基準分解、arXiv:2411.15594）、LLM-as-a-Judge の調査（偏り・一貫性・検証の整理、arXiv:2309.13308 系の survey）、AutoCalibrate（判定者の較正）。

## 決定

### 1. 基準別の判定を返させ、重み付きで合成する

応答スキーマを `{ criteria: [{ id, reason, score: number | null }], reason }`（strict）にする。各基準はルーブリックの id で正確に 1 回現れ、`score` はその基準の段階のいずれか、`null` は「与えられた情報では判定できない」（理由必須）。合成は Σ(weight × score) / Σ(weight) を **判定できた基準だけ** で行い、全基準が null なら `JUDGE_UNASSESSABLE`。基準別スコアは事例の `scores[]` に `"<metricId>:<criterionId>"` で並べ、既存の統計・実験比較・品質ゲートに手を入れずに基準ごとの比較を成立させる。

### 2. 根拠先出し・長さ中立・修復 1 回

スキーマとプロンプトで各基準の `reason` を `score` より前に置く。プロンプトに「長さ・冗長さ・体裁・断定口調・専門用語それ自体に報酬を与えない、ルーブリックだけで判定する」「基準は独立に判定する」「情報不足なら null」を明記する。契約違反（スキーマ・基準 id の過不足・段階に無い値・空の理由・JSON 破損・空応答）は違反を列挙して **1 回だけ** 修正を求め、再違反は `JUDGE_SCHEMA`。provider 例外はここでは再試行しない（一時障害の再試行は実験側の責務）。

### 3. 判定契約と判定コストをレコードに残す

`contract = { promptHash, rubricId, rubricVersion }`。`promptHash` はプロンプト版マーカー + ルーブリック JSON + 応答スキーマの sha256 先頭 16 hex で、文面を変えるときは版マーカーを上げる。`usage` は判定に使ったトークン（修復・全サンプル分の合計）。

### 4. 軌跡と履歴を tracePolicy の下で渡す

ルーブリックに `tracePolicy`（`optional` / `required` / `forbidden`、既定 `optional`。既存データは `optional`）を追加。turn 事例は Run の `tool-call` / `tool-result` から `{ name, arguments, resultSummary }`（出力プレビュー先頭 10 行）を、scenario 事例は最終応答を除く会話を `history` として、**untrusted data ブロックの内側** に渡す。上限は 20 件・各 2,000 文字。`required` で軌跡が無ければ `JUDGE_INPUT`。

### 5. k サンプル中央値と分散

実験に `judgeSamples`（1〜5、既定 1）を追加。2 以上なら温度 0.5 で独立に k 回判定し、合成は中央値、基準別は判定できたサンプルの中央値、理由は中央値に最も近いサンプルのもの。`dispersion = { min, max, stddev（母） }` と `uncertain = (max − min ≥ 0.25)` を記録し、失敗したサンプルは捨てて `samples` に実数を残す。

## 検討した代替案

- **合成を判定者に任せ、基準別スコアは参考情報にする**: 重みの適用が判定者ごとにぶれ、段階外の値を検出できない。合成はサーバーで決定的に行う方が再現性が高い。
- **段階外の値を最寄りの段階へ丸める**: 判定者の契約違反を黙って直すことになり、判定の質の劣化を隠す。修復依頼で判定者自身に直させ、直らなければ失敗として見せる。
- **判定者ごとの較正（AutoCalibrate）を同時に入れる**: 基準別スコアと契約の指紋が揃わないと較正の対象が定まらない。まず観測可能にし、較正は後続。
- **軌跡を常に渡す**: 応答だけを見せたい（ツール利用を評価に混ぜたくない）ルーブリックもある。`forbidden` を残す。
- **多数決や平均**: 中央値は外れ値サンプルに強く、段階の離散値と相性が良い。

## 帰結

- 判定レコードは基準別の理由とスコア、ばらつき、コスト、契約の指紋を持つ。UI は基準ごとの根拠と「判定が割れている」印を出せる。
- 判定契約の指紋が変わったら、以前の実験との比較は「判定者が変わった」ことを踏まえて読む必要がある（自動での無効化はしない）。
- 判定コストは `judgeSamples` に比例する。既定 1 なら従来と同じ呼び出し回数（＋修復が要るときの 1 回）。
- 旧形式の判定（`{ score, reason }`）は契約違反として修復対象になる。judge スロットのモデルが基準別 JSON を返せない場合は `JUDGE_SCHEMA` で失敗レコードになる。
- scenario 事例には軌跡が無い（ScenarioRun がトレースを保持しない）。`tracePolicy: required` は scenario 事例では必ず `JUDGE_INPUT` になる。転写された Run のトレースを引く配線は後続。
- 旧レコード・旧ルーブリック・旧実験はそのまま読める（新項目はすべて任意、既定は `optional` / `1`）。
