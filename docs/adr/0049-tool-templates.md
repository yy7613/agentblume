# ADR-0049: ツールテンプレートを外部ファイルで持ち、「選んで埋める」で Tool を作る

- Status: Accepted
- Date: 2026-09-20
- 関連: [implementation/v43](../../implementation/v43-tool-templates.md)（契約の正本）/ [templates/tools/README.md](../../templates/tools/README.md)（書き方）/ [ADR-0048](./0048-staged-tool-generation.md)（段階的ツール生成）/ [ADR-0047](./0047-factory-lessons-from-estat.md)（e-Stat での実測）

## 文脈

ADR-0048 で、Tool の生成を「小さな目的別タスク + 決定的コンパイラ」に分けた。モデルはグラフの JSON を書かず、`ToolSpec` という閉じた語彙の断片だけを決める。これでローカル 12B の機械的な書き間違いは構造的に消えるが、2 つの限界が残る。

- **作れる形がコードに埋まっている**。`ToolSpec` とコンパイラが表せるのは「期間・カテゴリで絞る / 結合 / 計算列 / 並べて返す」まで。前期比（時系列分析の comparison）、期間内の統計、相関、ランキングのような構成は、ノードとしては既にあるのに Factory からは作れない。語彙を足すたびにコードとテストを足すことになる。
- **人が使えない**。コンパイラは Factory の内部部品で、Tool Builder で手で組む人は相変わらず空のキャンバスから始める。分析ノードの設定（`interval`・`comparison.lag`・`groupBy` の組み合わせ）を正しく書くのは、人にとっても易しくない。

e-Stat の実測（ADR-0047）では、エージェントが前年比や倍率を**暗算**していた。決定的に計算できるノードがあるのに、それを組み込んだ Tool を誰も（モデルも人も）作れていなかった。

## 決定

1. **Tool の構成をテンプレートとして外部ファイル（JSON）で持つ**。1 ファイル 1 テンプレート。ノード・エッジ・引数・説明文をファイルに書き、可変部分だけを**スロット**として宣言する。
2. **スロットは型つきで、選択肢は決定的に作る**。`dataSource` / `column`（役割: 期間・カテゴリ・値・文字）/ `joinKeys` / `choice` / `number` / `text` / `intent`。列や結合キーの候補は Stage 0 のプロファイルから絞る。必須スロットに候補が無いテンプレートは、そのデータには出さない。
3. **モデルの仕事は 2 つだけ**: `select-template`（候補の id から選ぶ。`none` も可）と `fill-slots`（スロットごとに enum から選ぶ）。どちらも ADR-0048 のタスクランナーで回す。
4. **実体化は純関数**。置換（`$slot`・`{{ }}`・`$each`・`$concat`・`$number`・`$profile`・`$argument`・`$intent`）と `when`（任意スロットが空ならノードを外して前後を繋ぐ）だけを持つ、小さな宣言的な仕組みにする。テンプレートに式や制御構文は持たせない。
5. **抜け道を作らない**。実体化したグラフは、手で作った Tool と同じ検査（構造・スキーマ伝播・設計時プレビュー・保存時の検証）を通る。
6. **順番はテンプレート → 段階的生成 → 一括 ToolSmith**。当てはまるテンプレートが無い・モデルが `none` を選んだ・検査を通らない場合は、理由をイベントに残して次へ落ちる。
7. **計算は固定の式か分析ノードでテンプレートに書く**。比率・百分率は `calculate` の固定式（`[{{numerator}}] / [{{denominator}}] * {{scale}}`）、前期比は時系列分析、統計・相関は分析ノード。自由な計算だけ `intent` スロットで式提案（ADR-0046）に任せる。
8. **人も同じファイルを使う**。Tool Builder の「テンプレートから作成」は、同じ一覧・同じ候補・同じ実体化を API 経由で使う。
9. **壊れたファイルは読み飛ばし、理由と直し方を見せる**。利用者のフォルダ（`AGENTCONTEXT_TOOL_TEMPLATES_DIR`）を足せて、同じ `id` は後勝ち。再起動は要らない。

## 理由

- **高度な構成を「選ぶだけ」にできる**。分析ノードの正しい組み合わせは、一度テンプレートに書けば全員（小さなモデルも人も）が使える。モデルに要るのは「前年比が要る → period-change」という判断だけになる。
- **語彙の拡張がコード変更でなくなる**。新しい構成はファイルを 1 つ足せば使える。利用者・導入先が自分の業務の形を足せる。
- **説明文と引数の契約をテンプレート作者が一度だけ丁寧に書ける**。「日付は期間の開始日」「粒度は必須」「この列から答え、暗算しない」のような、実測で効いた指示をテンプレートに固定できる。
- **検証可能**。テンプレートは固定データに対して実エンジンで実体化・実行するテストを持てる（値まで検証する）。モデルが毎回書くグラフには、これができない。

## 検討した代替案

- **`ToolSpec` の語彙をコードで増やし続ける**: 構成ごとにコンパイラ・検証・テストが増える。利用者は足せない。段階的生成は「テンプレートに無い形」の受け皿として残す。
- **テンプレートを TypeScript のコードで持つ**: 型は付くが外部化できず、利用者が足せない。JSON + JSON Schema + 読み込み時の検査で、書き間違いは十分に捕まえられる。
- **YAML**: 人には読みやすいが、依存が増え、JSON Schema によるエディタ補完と相性が落ちる。
- **汎用のテンプレート言語（Handlebars 等）で JSON 文字列を組む**: 文字列置換で JSON を作ると、型（配列・数値）と引用符の事故が起きる。JSON の値としての置換（`$slot`）と文字列への埋め込み（`{{ }}`）を分けた最小の仕組みにした。
- **モデルにテンプレートを改変させる**: 「選んで埋める」の利点（検証済みの構成）が失われる。合わない場合は段階的生成へ落とす。

## 結果・影響

- 標準テンプレートを 10 本同梱する（時系列の取り出し / 最新値 / ランキング / 前期比 / 期間内の統計 / 横並びの結合（2 ソース・3 ソース）/ 2 ソースの比 / 相関 / 自由な計算列）。
- Factory の Tool 1 本あたりのモデル呼び出しは、テンプレート経路で 2 回（選択・スロット）+ 式提案（`intent` があるときだけ）。
- テンプレートの `id` と `version` は `tool_generated` イベントに残る（どの構成から作られたかを後から追える）。
- テンプレートが参照するノードの config 契約が変わると、テンプレートが壊れる。標準テンプレートは実エンジンのテストで守り、利用者のテンプレートは読み込み時の検査と `invalid` の表示で気づけるようにする。
- 非スコープ: テンプレートの GUI 編集・共有、`formatVersion` の移行ツール、テンプレートからの Skill 生成。
