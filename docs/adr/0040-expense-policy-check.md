# ADR-0040: 経費精算の規程チェック（3 値判定・理由コード・利用者が持つ規程）

- Status: Accepted
- Date: 2026-09-14（実装: 2026-09-15。設計からの差分は docs/21 §19）
- 関連: [docs/21-expense.md](../21-expense.md) / [ADR-0038](./0038-journal-two-stage-judgment.md)（仕訳の 2 段階判定）/ [ADR-0039](./0039-business-feature-registration.md)（業務の登録点）/ [ADR-0034](./0034-domain-primitive-tiers-and-id-types.md) / [ADR-0035](./0035-domain-shared-kernel-and-boundary-conversion.md)

## 文脈

2 つ目の業務テンプレートとして、従業員の立替経費（領収書）を会社の規程に照らしてチェックし、承認して精算する機能を入れる。仕訳（ADR-0038）の判定は「迷わず仕訳できるか」だったが、経費は「**この支出を会社として認めてよいか**」を問う。次の点で設計が分かれる。

1. **規程は会社ごとに大きく違う**。費目の切り方、上限額（1 件・1 人あたり・1 泊あたり）、領収書やインボイス登録番号の要否、事前承認が要る条件、どの違反を差し戻しにしてどれを確認で済ませるか。交際費の「1 人 10,000 円以下」のような税務上の基準も、税込で見るか税抜で見るか、そもそも社内基準を別に置くかは会社が決める。
2. **判定の結果は「可 / 不可」の 2 値では足りない**。登録番号が無いレシート、参加人数が 1 人多ければ基準内に収まる飲食代、同じ日・同じ店・同じ金額の 2 件は、規程上は人の判断が要る。一方で金額の無い明細や未来の日付は、確認するまでもなく申請者に直させるべきものである。
3. **判定を LLM に任せるか**。規程の文章と領収書を渡して「規程に沿っているか」を答えさせる設計は導入が速い。しかし同じ申請が実行のたびに通ったり通らなかったりすると、承認者も申請者も判定を信用しなくなり、差し戻しの理由も説明できない。
4. **帳票の読取には実測で分かった誤りの型がある**（登録番号の桁数、税率別金額、取引日と発行日の取り違え、精算書で発行者が空になる）。読取は仕訳で既に作り込んでいる。
5. **承認は責任の所在そのもの**。誰が、どの違反をどういう理由で認めたかが後から問われる。
6. 承認済みの経費は仕訳（費用 / 未払金）に流れる。仕訳のコードは別の担当が並行して触っている。

## 決定

### 1. 判定は決定的な純粋関数で「通過 / 要確認 / 差し戻し」の 3 値にし、理由コードを列挙する

`checkClaim`（`src/domain/expense/check.ts`）は **申請・規程・重複候補・判定日だけを引数に取る純粋関数**にする。理由は**閉じた列挙（27 コード）**で、各コードはカタログ（`reason-codes.ts`）に対象（明細 / 申請）・既定の重さ（`review` / `return`）・上書きできる値・電帳法の検索要件のどれに当たるか・導線先を持つ。申請の判定は最も重い理由で決まる（理由なし = 通過、`review` だけ = 要確認、`return` が 1 件でもあれば差し戻し）。

評価順を固定し、前提が欠けたら依存するチェックを打ち切る（金額の無い明細に「上限超過なし」を出さない）。理由は評価順に並べ、画面は根本の原因から「原因 → 次の一手 → 修正場所へのボタン」で見せる。

**理由コードの集合はコードに持ち、重さと数値はデータに持つ**。どんな違反を検出できるかは実装が約束する契約で、会社ごとに変わるのは「その違反をどれくらい重く見るか」と「閾値」だからである。

### 2. 段階 2 は LLM ではなく人の確認にする

要確認（`review`）の理由は、承認者が 1 件ずつ**確認済み（根拠コメント必須・監査対象）**にする。差し戻し（`return`）の理由は確認済みにできず、申請者が直して再チェックするしかない。承認は「差し戻し理由 0 件・未確認の要確認 0 件・判定が古くない」ときだけ押せる。差し戻しの文言は理由コードの申請者向け文言から既定形を作り、人が編集してから送る。

仕訳（ADR-0038）の Stage 2 は LLM ヒアリングだったが、経費では**判定にも確認にも LLM を使わない**。仕訳の Stage 2 はルールという「次回から決定的に使える資産」を作るので LLM を使う価値があったが、経費の確認は個々の支出を認めるかどうかの判断で、資産にならず、責任の所在を曖昧にするだけである。LLM を使うのは読取（§4）と、将来の規程の作成（帰結を参照）に限る。

### 3. 規程はワークスペースのデータにし、初期テンプレートは「保存しない初期値」にする

費目（科目・税区分・証憑とインボイスの要否・必須項目・上限）、申請ルール、事前承認条件、理由コードの重さの上書き、仕訳連携の設定を `ExpensePolicy` 集約としてワークスペース単位で保存する。**上限額や費目名の列挙をコードに持たない**（`default-policy.ts` の初期テンプレートだけが例外）。交際費の 1 人 10,000 円も初期値である。

事前承認条件は汎用の条件式にせず、「費目 × 1 件の金額以上 × 1 人あたりの金額以上」の AND という**構造化した形**に限る。費目の属性も構造化したフィールドで持つ。

規程を保存したことが無いワークスペースでは初期テンプレートを返すが**保存はしない**（ADR-0038 §2 と同じ理由）。代わりに判定が `policy-unreviewed`（要確認）を出し、最初に規程を見直す導線にする。費目は id で参照し、削除は論理削除にする。

### 4. 読取は仕訳のユースケースをポート越しに再利用し、値は補正せず警告を要確認にする

経費の application 層に `ReceiptReaderPort` を定義し、`composeExpense`（ADR-0039）が仕訳の組み立て結果の `ExtractJournalDocumentUseCase` を包んで注入する。経費専用の抽出プロンプトは作らない。読取結果は経費の事実へ写し（精算書の発行者は支払先にせず申請者の候補にする、精算書の明細行は日付を空のまま分割する）、仕訳側の整合チェックの警告は `receipt-extraction-warning` として人に見せる。**読み取った値を自動で補正しない**。

### 5. 仕訳連携は `JournalDraftSink` ポートで仕訳の保存ユースケースへ渡し、1 明細 = 1 仕訳下書きにする

経費の application 層に `JournalDraftSink` を定義し、`composeExpense` が仕訳の `SaveJournalEntryUseCase` を包む（仕訳の組み立て結果を受け取るため、`root.ts` の呼び出し 1 行の変更を登録点の担当へ要求する。docs/21 §18.1 S-1）。仕訳は `draft` で作られ、確定は仕訳画面で人が押す。1 仕訳は 1 つのインボイス区分しか持てないので、支払先・登録番号が明細ごとに違う経費は **1 明細 = 1 仕訳**にする。作成前に全明細を検査し（科目の欠落・内訳と金額の不一致）、問題があれば 1 件も作らない。途中で仕訳側に拒否されたら作成済みの分を記録し、残りを再開できるようにする。**仕訳側のコードは変更しない**。

依存の向きは expense → journal の一方向で、expense の domain が import してよいのは仕訳 domain の純関数と値型（正規化・税・CSV）だけ、expense の application は仕訳の application を import しない。

### 6. 重複検出は派生の索引テーブルで引く

申請の本体は `record_json` に置き、絞り込み列だけを列に出す（仕訳 v5 の方針）。そのうえで、申請をまたぐ重複（支払先・取引日・金額の組、および同一画像のハッシュ）を全申請を読まずに引くため、`expense_item_keys` を**派生データ**として申請の保存と同じトランザクションで入れ直す。支払先が空の弱い鍵での一致は、規程の重さに関係なく要確認に留める。

### 7. 承認は `approve` 権限、エージェントのツールは参照のみ

承認と承認取消は既存の認可アクション `approve`（Publisher 以上）を要求する。自己承認の禁止はロールではなく規程の設定にする。エージェントから呼べるのは参照だけ（添付領収書の試算チェック・申請一覧・規程）で、チェック結果の保存・確認済み・差し戻し・承認・精算・仕訳下書きの作成はツールにしない（仕訳 docs/20 §14.1 と同じ）。

## 検討した代替案

- **LLM に規程適合を判定させる**: 導入は速いが、同じ申請の結果が揺れ、差し戻しの理由を列挙できず、承認者の責任も説明できない。規程の数値比較は決定的に書ける。
- **可 / 不可の 2 値にする**: 人の判断が要るケースをどちらかに寄せることになり、厳しくすれば差し戻しの山、緩くすれば見逃しになる。
- **重さを固定する（コードごとに差し戻し / 要確認を決め打ち）**: 「登録番号が無ければ差し戻し」の会社と「確認で済ませる」会社の両方に応えられない。一方で「金額が無い」を要確認に下げられても意味が無いので、上書きできる範囲はコードごとに制限する。
- **規程を汎用の条件式（仕訳ルールの `conditions` のような DSL）で持つ**: 表現力は高いが、経理担当が上限額を 1 つ直すのに条件式を読む必要があり、導入で詰まる。経費の規程に現れる項目は限られるので、構造化したフィールド + 限定した事前承認条件を選ぶ。表しきれない規程が出たら、フィールドを足す（理由コードの追加と同時に行う）。
- **申請全体で 1 つの複合仕訳にする**: 仕訳のインボイス区分・登録番号がエントリに 1 つなので、明細ごとの経過措置が表せない。
- **経費専用の抽出プロンプトを作る**: 読取の誤読対策（登録番号 13 桁・取引日と発行日の区別・0 円税率行を作らない）を二重に保守することになる。経費固有の項目（参加人数・目的）は仕訳側の抽出に追加項目として足す方を要求する（任意）。
- **重複を全申請の読み込みで検出する**: 件数に比例して遅くなり、画像を含む本体を読むことになる。
- **承認を `edit` 権限にする（仕訳の確定と揃える）**: 入力する人と支払いを認める人を分けられない。

## 帰結

- 判定が純粋関数なので、27 コードの出る / 出ないと境界（上限ちょうど・1 人あたり・期間の端・判定日）を表形式のテストで固定できる。規程の数値を変えれば結果が変わり、変えなければ変わらない。
- 規程の数値がデータなので、**導入直後は初期テンプレートとの差で差し戻しが多く出る**。`policy-unreviewed` と重さの上書きで緩和するが、根本の解決は規程を作る支援（フェーズ 3 のヒアリング: LLM が規程の**案**を作り、利用者が差分を見て保存する。判定は決定的なまま）になる。
- 理由コードの集合がコードにあるので、会社固有の新しいチェック（例: 経路検索による交通費の妥当性）はコード変更で足す。規程のフィールドとカタログを同時に増やす。
- 読取を仕訳と共有するので、仕訳側の読取の改善がそのまま経費にも効く。逆に、読取の警告文を文字列で解釈すると壊れやすいので、構造化した読取メタは仕訳側への任意の変更要求として出す。それまでは警告文をそのまま人に見せる。
- 仕訳下書きは仕訳側で削除できるが、経費側の連携記録は MVP では追従しない。
- 仕訳 domain の純関数に依存するため、仕訳側の正規化・税の変更が経費の判定に波及する。依存してよい関数を限定し、将来は `domain/shared` へ移す。
- SQLite のスキーマは version 6（`expense_policy` / `expense_claims` / `expense_receipts` / `expense_item_keys` の追加のみ。仕訳を含む既存データはそのまま）。証憑画像は申請から分けた `expense_receipts` に 1 件 8 MiB 上限で同梱する。
- MVP は電子帳簿保存法の検索要件（日付・金額・取引先）が揃っているかを判定するだけで、真実性要件（訂正削除の履歴）や保存期間の管理は行わない。この範囲は画面と docs に明示する。
