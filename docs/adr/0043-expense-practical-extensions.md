# ADR-0043: 経費精算の実用化（人と承認・お金の流れ・入力と規程の自動化）を判定の拡張点と先行する骨格で並行して足す

- Status: Accepted（docs/21 §20.17 の判断は 2026-09-15 に確定。本 ADR の §6・§9・§13 と「決定した判断」に反映）
- Date: 2026-09-15
- 関連: [docs/21-expense.md](../21-expense.md) §20（本 ADR の詳細設計）/ [ADR-0040](./0040-expense-policy-check.md)（規程チェックの判定モデル）/ [ADR-0039](./0039-business-feature-registration.md)（業務の登録点）/ [ADR-0038](./0038-journal-two-stage-judgment.md)（仕訳の 2 段階判定とヒアリング）/ [ADR-0041](./0041-receivables-payment-matching.md)（入金消込。振込名義の正規化）

## 文脈

経費精算の MVP（ADR-0040、docs/21 §1〜19）は「1 人の経理担当が立替経費を取り込み、規程でチェックし、承認して CSV と仕訳下書きに流す」までを作った。実際に会社で回すには次が足りない。

1. **申請者が自由文字列**である。部門・上長・振込口座・通勤定期を持てず、多段承認・振込データ・定期区間の控除のどれも作れない。既存の申請（`record_json`）は氏名の文字列しか持っていない。
2. **承認が 1 段**で、`approve` 権限を持つ誰でも押せる。部門長 → 経理のような経路を会社ごとに決められない。一方で、この製品は資格情報を求めない単一ユーザーモード（`subject = single-user`、全ロール）でローカル単独でも使われており、「指定の人しか承認できない」を素直に入れると 1 人では承認できなくなる。
3. **支払の出口が CSV だけ**で、銀行へ渡す全銀協形式の振込データが無い。全銀協形式は 120 バイト固定長・半角カナのみで、銀行ごとに改行・記号・名称欄の扱いが違う（docs/21 §20.6 の調査）。
4. **お金の流れの例外**（仮払金の精算、法人カード払いと立替の二重計上、月次の集計）が扱えない。
5. **入力の弱点**: 12B 級の vision モデルの読取は、登録番号の桁・税率別金額・取引日と発行日・精算書の支払先で誤る。参加人数や区間は仕訳の読取プロンプトにそもそも無い。交通費は運賃の妥当性を見ていない。
6. **規程づくりの負担**: 初期テンプレートとの差で導入直後に差し戻しが多発する（ADR-0040 帰結）。
7. これら 9 ユースケースを **3 人が並行して実装する**。経費の共有ファイル（`claim.ts` / `policy.ts` / `check.ts` / `serialization.ts` / `expense-routes.ts` / `ExpensePage.tsx` / 組込みツール）を同時に書き換えると衝突し、git 操作ができない状況では解消もできない（ADR-0039 と同じ事情が業務の内側で起きる）。
8. v6 は利用者の DB に適用済みの可能性があり、v7（receivables）・v8（contract）は他業務の版である。

## 決定

### 1. 骨格担当が型・保存・理由コード・登録点を先に確定し、3 系統はその上に新規ファイルだけで足す

「人と承認（A）」「お金の流れ（B）」「入力と規程（C）」の 3 系統に分け、**骨格担当 1 人**が先に次を作る: 全集約の型と不変条件と直列化、v9 のマイグレーション、リポジトリのポートと SQLite / InMemory の実装と共有契約、新しい理由コード 16 件のカタログと全文言（画面・申請者向け・ツール向け）、判定の拡張点、API のサブルート登録点、画面のスロット、各系統のスタブ、テスト用フィクスチャ。3 系統の担当は、自分の系統のディレクトリ（`domain/expense/<people|money|input>/` など）とスタブを書き換え、骨格の既存ファイルには触れない。系統をまたぐ依存（振込と交通費は従業員マスタに、集計は部門に依存する）は、**骨格が型・リポジトリ・読取ポート・フィクスチャを完成品で先に置く**ことで解消する。骨格のファイルは引き渡し後に凍結し、変更は骨格担当への依頼で直列化する。

### 2. 判定の拡張は「系統ごとの検査関数（contributor）」と「事実を集めるポート」で差し込み、判定は純粋関数のまま

`checkClaim` に `extensions`（系統ごとの事実: 申請者の従業員・承認経路の解決結果・仮払・カード利用の候補・定期区間・運賃）を足し、骨格が定める `ExpenseCheckContributor`（出してよいコードの集合・明細の理由・申請の理由）を 3 つ並べる。事実は application の `ExpenseCheckFactsProvider` が索引から集め、判定そのものに I/O もモデルも入れない。理由の並びは**カタログの順（= 評価順）で安定ソート**し、既存 27 コードの相対順と打ち切り規則は変えない。contributor は既存の理由の有無と、解決済みの費目・金額・日付を受け取って打ち切る。コードの集合はコードに持ち、重さと閾値は規程のデータに持つ（ADR-0040 §1 を維持）。

### 3. 従業員マスタを申請者の参照先にし、申請には表示用の写しを残す。名前だけで自動の紐付けはしない

`ExpenseEmployee`（社員番号・氏名・部門・上長・ログイン ID・振込口座・通勤定期・有効）を足し、申請者は `claimant.employeeId` で参照する。既存の `claimant.name` などは**申請時点の写し**として残し、既存の申請はそのまま読める。移行は SQL で書き換えず、「紐付け候補」画面で社員番号の一致 → 名前の一意な一致の順に**候補を示し、人が確定する**。同姓同名や表記揺れを黙って結ぶと、他人の口座へ振り込む事故につながるため。マスタに有効な従業員が 1 人もいない間は紐付けを求めない（`claimant-unlinked` を出さない）ので、マスタを使わない運用は MVP のまま動く。

### 4. 現在の利用者は `Principal.subject` と従業員の「ログイン ID」で結び、単一ユーザーモードでは代理承認として詰まらせない

新しい認証の仕組みは作らない。トークン認証の `subject` を従業員マスタの `loginSubjects` に登録すると、その人が申請者本人か・現在の段の承認者かを決定的に判定できる。単一ユーザーモード（`subject === SINGLE_USER_SUBJECT`）は「そのマシンの利用者が唯一の主体」なので、どの段も**代理承認（コメント必須・履歴と監査に代理の印）**として押せる。トークン認証では規程の `approval.proxyGroupId` に入っている従業員だけが代理できる。

### 5. 承認経路は規程のデータにし、段の承認者は承認時に決定的に解決して申請へ写す

`ExpensePolicy.approval.routes[]`（条件: 費目・申請合計・部門の AND → 段 1〜5: 申請者の上長 / 部門長 / 指定の従業員 / 承認グループ / approve 権限を持つ誰でも）を足す。どの経路にも当たらなければ `defaultSteps`（既定は 1 段の「approve 権限を持つ誰でも」）で、**経路を設定しない会社は MVP と同じ 1 段承認**になる。1 段目の承認で経路を解決して申請の `approvalFlow` に承認者の写しを保存し、以後のマスタ変更で承認者は変わらない（変えるなら承認取消）。申請の状態に `in-approval` を足す。規程の変更で判定が古くなったら段の承認を捨てて再チェックへ戻す。承認者が決まらない経路（上長が未設定など）はチェックの時点で理由コードとして見せ、直す場所へ導線を出す。

### 6. 全銀協の総合振込は、最も狭い文字集合への決定的な変換と出力前の点検で作り、銀行差は設定データにする

レコード（ヘッダー 1 / データ 2 / トレーラー 8 / エンド 9、各 120 バイト）は公開仕様の一致点どおりに純関数で組み、Shift_JIS の半角だけで書く（JIS X 0201 の範囲なので対応表の変換だけで足り、外部ライブラリは要らない）。受取人名は「全角カナ → 半角・小書き → 並字・長音 → ハイフン・英小文字 → 大文字」の**書式の変換だけ**を行い、変換後の名義を画面に見せる。漢字・中点など変換できない文字、30 バイト（濁点は 1 バイトとして数える）超、口座番号・銀行コードの桁不正、口座の未登録は**出力前に理由付きで止め**、従業員の口座欄へのボタンを出す。改行の有無・EOF・銀行名欄・手形交換所番号・振込指定区分・許容記号の広さ・1 ファイルの件数上限は、銀行により違うので振込元の設定データに持つ。

振込口座の口座番号は **`SecretCipherPort` で封緘して保存する**（利用者の決定。docs/21 §20.17-1）: 7 桁に揃えた口座番号を、モデル設定・MCP 設定と同じ鍵（DB の外の鍵ファイル）で封緘した値として `record_json` に置き、封緘の `hint`（末尾 4 桁）で一覧・詳細・ツールの伏せ字を出す（開封しない）。平文は口座番号を含む出力（振込データの作成と再ダウンロード・口座つき従業員 CSV）の瞬間だけ `application/expense/bank-account-secrets.ts` で開封し、その出力は `approve` 権限と監査を要求する。受取人名が変換後 30 バイトを超えたら切り詰めずに出力前に止め、従業員マスタの名義カナの欄へ導線を出す（利用者の決定。§20.17-7）。口座の変更は従業員の履歴に必ず残し、振込データの点検で「直近に口座を変えた従業員」を確認必須の警告にする（口座のすり替えによる不正の抑止）。振込データは作成時点の口座の写しを持つ振込バッチとして保存し、同じ申請を 2 つのバッチへ入れない。

### 7. 仮払金は独立した集約にし、精算の差額は相殺せずに向きで分ける

`ExpenseAdvance`（申請 → 承認 → 支払済み → 精算中 → 精算済み）を足し、経費申請は `claim.advanceId` で仮払を指す（正本は申請側の 1 か所）。精算は紐付く申請の承認額の合計と仮払額の差で決まり、正なら追加支給（振込データには差額だけ）、負なら返金の受領を記録するまで精算済みにしない、0 ならそのまま精算済み。他の申請の支払額と返金を**相殺しない**（誰のどのお金かが帳簿と振込の両方で追えなくなるため）。仕訳は支払時「仮払金 / 預金」、精算時「未払金（規程の貸方科目） / 仮払金（+ 返金の預金）」の下書きを `JournalDraftSink` 越しに作る。

### 8. 法人カード明細は保存した列マッピングで取り込み、許容差つきの 1 対 1 の決定的な照合で二重計上を理由コードにする

カード明細 CSV は利用者が保存する列マッピング（ヘッダの署名で次回から自動で選ぶ）で取り込み、CSV の純関数は仕訳 domain のものを使う（receivables のコードは import しない）。照合は金額（許容差）・日付（許容日数）・加盟店名の正規化キーで強い / 弱い一致を作り、強さ → 日付差 → 金額差 → id の順で 1 対 1 に割り当てる。**立替として申請された明細がカード利用と一致したら `card-charge-claimed`**（弱い一致は常に要確認）。会社払いの明細を申請に含める運用は規程のフラグで選び、選んだ場合は振込から除き、一致するカード利用が無ければ `corporate-payment-unmatched` にする。未申請のカード利用と対象外の印は台帳で扱い、理由コードにはしない（申請が無いため）。

### 9. 集計は domain の純関数にし、エージェントには read-only のツールを 4 本足す

月 × 部門 × 費目 × 申請者 × 状態の集計は、明細の索引行を入力にする純関数で作り、画面・CSV・ツールが同じ関数を使う。ツールは `expense_summary` / `expense_advances` / `expense_card_transactions` / `expense_fares` の 4 本で、保存・承認・支払・取込・照合はツールにしない（ADR-0040 §7）。口座番号と通勤定期はツールに出さない。`group_by` を引数で受けるための共有側の変更（行ソースへツールの引数を渡す G-2。`RowSourceRowsInput.arguments`）は入れた（§20.17-3）ので、`expense_summary` は集計の粒度・期間の範囲・状態を行ソースが受け取る。

### 10. 経費専用の追加読取は「印字どおりの文字列」を読ませ、変換と照合はコードで行う。仕訳の読取は変えない

仕訳の読取（ADR-0040 §4）はそのまま使い、経費 BC が `BusinessCompositionContext.modelProvider` で**追加の構造化抽出**（登録番号・日付・支払先の印字どおりの文字列、参加人数の文字列と氏名、目的の手がかり、区間）を行う。数値化・日付化・桁数の判定・支払先キーの比較はコードが行い、12B 級のモデルに正規化をさせない。仕訳の読取結果は上書きせず、空欄だけを候補として埋めて警告にする。2 回の読取の食い違い・発行日で代用した取引日・人が確認していない読取候補は、それぞれ理由コードで見せる。構造化した読取メタが経費側で得られるので、仕訳への変更要求 R-1（docs/21 §18）は不要になる。追加読取は遅いので既定は off とし、明細ごとに「追加で読む」を押せるようにする。

### 11. 交通費は運賃マスタと通勤定期（駅の並び）で決定的に照合し、外部の経路検索は使わない

運賃マスタ（駅の並び・IC / 切符・片道運賃・双方向・有効期間・駅名の別名）と、従業員の通勤定期（経路順の駅の並び・有効期間）はどちらも利用者のデータにする。明細の区間の両端が定期の駅の並びに含まれれば定期内（差し戻し）、片側だけなら一部重複（要確認。運賃マスタに残りの区間があれば金額の候補を文言に出すが、金額は直さない）、金額が「登録運賃 × 回数 + 許容差」を超えれば要確認。路線図を持たないので「駅の並び」に無い乗換の重なりは検出できないことを制約として明示する。

### 12. 規程のヒアリングは LLM に規程案と根拠の引用を出させ、引用の実在をコードで検査し、差分を人が項目ごとに選ぶ

社内規程の文章を貼る / 質問に答えると、モデルが規程の**案**（費目・上限・必須・事前承認・承認経路）と、変更ごとの規程文の引用を構造化出力する。案は `createExpensePolicy` を通る部分だけを残し（通らない部分は理由付きで捨てる）、引用が規程文に実在するかを正規化した部分文字列で検査して「根拠あり / 根拠なし」を付ける。現在の規程との差分を項目ごとに並べ、利用者が選んだ項目だけを保存する（削除は無効化）。案を作った後に規程が変わっていたら 409 で作り直させる。**判定は決定的なまま**で、LLM は判定にも確認にも関与しない（ADR-0038・ADR-0040 §2 と同じ線引き）。

### 13. 保存は v9 の新しいテーブルだけで行い、既存の `record_json` はそのまま読める

v6 の文は変えず、`statementMigration(9, 'expense practical extensions', …)` で新しいテーブルと派生の索引テーブルを `CREATE … IF NOT EXISTS` だけで足す。`ALTER TABLE` は使わない（予約版の手前で版の刻みが止まる期間は開くたびに流し直され、`ADD COLUMN` は冪等に書けないため）。集計と絞り込みに使う派生の索引は、既存の申請から `json_each` / `json_extract` を使う `INSERT OR IGNORE … SELECT` で埋める（流し直しても冪等）。直列化は新しい項目をすべて省略可にし、無い項目は `create*` が既定値で補う。**読み込みだけでは `updatedAt` も判定の指紋も変えない**（指紋は未定義の項目と `claimant.employeeId` / `departmentId` を含めない）ので、既存の判定は古くならない。`MIGRATIONS` への v9 の追加は共有ファイルの変更として骨格担当が入れた（ADR-0039 の表の経費精算の版は「6, 9」）。

### 14. 判断が必要だった点の決定（docs/21 §20.17）

- 口座番号は封緘する（上の §6）。鍵を失うと振込データを作れなくなるが、DB ファイル単体の漏洩への強さを利用者が優先した。
- 申請の状態に `in-approval` を足す（上の §5）。経路が 1 段（既定）の承認は MVP と同じ記録（`approval` だけ）にし、既存の遷移とデータを変えない。
- G-2 を入れる（上の §9）。既存の仕訳・入金消込・契約の行ソースは引数を読まないので振る舞いは変わらない。
- 会社払い明細の受け入れの既定は off、社員番号は任意、振込の名義 30 バイト超は止める。
- 推奨案の採用: トークン運用の代理承認は `proxyGroupId` のメンバーに限る、振込確定時の支払仕訳は既定 off、仮払の承認は 1 段。

## 検討した代替案

- **系統ごとに経費の既存ファイルを直接書き換える（骨格を置かない）**: 理由コードの列挙・直列化・`ExpensePage.tsx` を 3 人が同時に触ることになり、ADR-0039 が避けた衝突が業務の内側で再発する。
- **系統ごとに別の業務（別画面・別 BC）にする**: 承認経路・仮払・カードはどれも同じ申請集約の状態と判定に効くので、判定の一貫性（同じ申請に 1 つの判定）が崩れる。
- **理由コードを系統ごとに動的に登録する**: カタログの網羅テスト（全コードに文言がある）と規程の `severityOverrides` の検証が実行時の登録順に依存する。閉じた列挙を骨格が先に確定する方が、系統の担当が文言を取り合わない。
- **申請者を名前の一致で自動移行する**: 同姓同名・表記揺れで他人に紐付くと、振込先と承認者が入れ替わる。候補を示して人が確定する。
- **認証を作り込み、申請者本人のログインと提出まで入れる**: 招待・パスワード・通知の設計が要り、ローカル単独利用を壊しやすい。既存の `subject` を従業員へ結ぶだけにし、本人提出は後回しにする。
- **承認経路を汎用のワークフロー定義（条件式・分岐・並列）で持つ**: 規程 DSL を避けた ADR-0040 の判断と同じ理由で、経理担当が読めなくなる。条件 3 種の AND と直列の段に限る。
- **口座番号を個人情報として平文で置き、応答の伏せ字・出力の権限・監査だけで守る**: 鍵ファイルを失っても振込データを作れるが、DB ファイル・バックアップ単体の漏洩で全従業員の口座が読める。伏せ字の表示は封緘の `hint` で開封せずに出せるので、封緘しても画面の使い勝手は変わらない。利用者が封緘を選んだ（docs/21 §20.17-1）。
- **全銀協形式を銀行ごとのプリセット（固定表）で持つ**: 固定表禁止の方針に反し、表に無い銀行で詰まる。銀行差は利用者が選ぶ設定値にし、既定は最も広く通る組み合わせにする。
- **受取人名が 30 バイトを超えたら切り詰めて警告にする**: 出力は止まらないが、銀行の名義照合で組戻しになる。利用者が止める方を選んだ（docs/21 §20.17-7）。
- **受取人名の禁止文字を自動で置き換えて出力する**: 中点をピリオドにするかスペースにするかは人が決めることで、黙って変えると銀行側の名義照合で組戻しになる。書式の変換だけを行い、判断が要る文字は止める。
- **カード利用と立替の差額や仮払の返金を他の支払と相殺する**: 振込の件数は減るが、帳簿と振込の突き合わせができなくなる。
- **経費専用の読取で仕訳の読取を置き換える**: 仕訳側で作り込んだ誤読対策を二重に保守することになる（ADR-0040 §4 の理由のまま）。追加の抽出に留める。
- **経路検索 API で運賃を引く**: 外部サービスへの依存・料金・社外への移動経路の送信が生じる。会社がよく使う経路は限られるので運賃マスタで足りる。
- **LLM に規程の差分を判断させて自動保存する**: 規程は以後のすべての判定の基準で、誤った上限が黙って入ると判定全体が信用を失う。引用の検査と人の選択を挟む。
- **申請の状態を増やさず `checked` のまま `approvalFlow` だけで承認中を表す**: 状態の値域は変わらないが、一覧・フィルタ・「あなたの承認待ち」・編集の禁止を状態で書けず、`checked` の意味が「承認できる」と「承認の途中」で割れる。`in-approval` を足した（docs/21 §20.17-2）。
- **v9 で既存テーブルに列を足す（`ALTER TABLE`）**: 予約版が残る期間の流し直しで失敗する。派生テーブルに分ける。

## 帰結

- 3 系統は骨格の引き渡し後に並行して進められる。骨格が大きくなる（型・リポジトリ・文言・スタブ）ので、骨格の完了までは系統の実装を始めない。骨格のファイルの凍結後に型の追加が要ったときは骨格担当への依頼になり、そこが直列の待ちになる。
- 理由コードは 27 → 43。規程の重さの表と画面の理由カードが長くなるので、画面は系統ごとの見出しで折りたたむ。
- マスタ・承認経路・振込元・カード・運賃を**設定しない限り MVP と同じ動き**になる（1 段承認・紐付けを求めない・定期控除も運賃照合もしない・カード照合しない）。実用機能は「準備状況」の一覧から段階的に有効になる。
- 口座番号は DB・バックアップ・振込バッチの写しに封緘値で載り、平文は振込データのファイルと口座つき CSV にだけ出る。鍵ファイル（DB の外）を失うと開封できず、振込データを作れない（口座の再入力で直る）ので、鍵ファイルをバックアップの手順に含めることを画面と docs に明示する。業務の組み立て文脈（`BusinessCompositionContext`）に封緘のポート（`secretCipher?`）が増えた。
- 全銀協形式は銀行差があるので、実銀行でのアップロード確認は利用者の環境でしかできない。サンプルの期待バイト列は公開仕様の一致点で固定し、銀行差の設定ごとに境界テストを置く。
- 追加読取とヒアリングは外部のモデルプロバイダを使う設定では規程文・領収書の氏名がモデルへ送られる。ヒアリングには従業員の氏名を渡さず、承認経路の案は「上長」「部門長」「承認グループ」の種類までに留める。
- 組込みツールのシードは既存の internalId を上書きしないので、`expense_claims` の説明文の更新は既存のワークスペースに届かない（列の追加は届く）。
- 仕訳のコードは変えない。`JournalDraftSink` の下書きに補助軸（部門）と出所（明細・仮払・カード・振込）を足し、composition が `SaveJournalEntryUseCase` へ渡すだけにする。
- `MIGRATIONS` への v9 の追加・`schema-migration.test.ts` の版の期待値・G-2（行ソースへのツールの引数）は共有ファイルの最小の変更として骨格が入れた（docs/21 §20.14）。他業務の行ソースは引数を読まないので振る舞いは変わらない。
