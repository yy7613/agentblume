# ADR-0048: ツール生成を「小さな目的別タスク + 決定的コンパイラ」に分ける

- Status: Accepted
- Date: 2026-09-20
- 関連: [implementation/v42](../../implementation/v42-staged-tool-generation.md)（契約の正本）/ [ADR-0047](./0047-factory-lessons-from-estat.md)（e-Stat での実測）/ [ADR-0046](./0046-calculate-expression-assistant.md)（式の提案）/ [docs/16](../16-agent-factory.md) Stage 2

## 文脈

Agent Factory の ToolSmith は、1 回のプロンプトで Tool のグラフ全体（ノード・エッジ・各ノードの config・引数宣言・説明文）を JSON で書く。e-Stat の実データとローカル 12B モデルで回した結果（ADR-0047 の第 3〜5 ラウンド）:

- 試行のたびに**別の**機械的な書き間違いが出た（`toInput` 欠落、`parse_period`、`sample` の位置、`dataSourceId: null`、日付引数の string 宣言、`keys` を文字列配列、agent-input 忘れ、`value` と `values` の重複）。1 試行 2〜5 分を使い、3 試行で Tool が 1 本もできない Run が続いた。
- 対策として提案の正規化（`normalizeProposedGraph`）を足し、通るようにはなった。ただし正規化の対象は「観測された書き間違い」の後追いで、機能（`in`・結合・期間の解釈）を足すたびに書き間違いの表面積が増える。
- 計算列（`calculate`）は ToolSmith の許可リストに無い。式の文法・関数表・検証・修復・標本試算を備えた式提案（ADR-0046）は Tool Builder の画面からしか呼ばれておらず、Factory が作るエージェントは差や比を**暗算**している（「LLM に計算をさせない」という製品の立場に反する）。

同じ時期に、開発側では人（オーケストレーター）がサブエージェントへ仕事を出すやり方が安定して機能していた。1 タスク 1 目的、契約（入出力の形）を先に固定、所有範囲を分ける、検証方法を指定する、失敗は担当へ理由つきで戻す、という進め方である。

## 決定

1. **Tool の新規作成を、小さな目的別タスクの列に分ける**。モデルに書かせるのは宣言的な仕様（`ToolSpec`）の断片だけで、グラフの JSON は書かせない。タスクは `decide-join`（結合時のみ）/ `decide-filters` / `decide-computations` / `decide-output` / `write-expression`。
2. **選択肢を閉じる**。列名・結合キー・粒度は、Stage 0 のプロファイルから作った `enum` の中から選ばせる。自由記述は引数名・計算列の名前・計算の意図文だけ。
3. **グラフは決定的なコンパイラが組む**（`compileToolSpec`）。ノード id・エッジ・`toInput`・束縛・引数宣言・設計時サンプル・説明文はコードが作る。コンパイラの出力は既存の構造検査・意味検査を必ず通る（テストで固定）。
4. **式は専用プロンプトへ別タスクで投げる**。計算列ごとに既存の式提案ユースケースを呼び、式を検証・修復・試算してからノードへ入れる。式が作れない計算列は**その列だけ**落として Tool は作る。
5. **差し戻しは担当タスクへ**。検査の違反から「どの決定が悪いか」を引き、そのタスクだけを理由つきで 1 回やり直して再コンパイルする。
6. **従来の一括 ToolSmith は残す**。段階的な経路が失敗したらフォールバックし、理由をイベントに残す。`FactoryOptions.toolGeneration` で切り替えられる（既定は段階的）。
7. **タスクランナーは再利用できる形で置く**（`runRoleTask`）。Planner など他のロールの段階化は別増分とする。

## 理由

- **書き間違いの表面積が、機能の数ではなく仕様の語彙で決まる**。ノード種別やポートの規約が増えても、モデルが触れるのは「どの列で絞るか」「複数か 1 つか」のような決定だけで、増えない。
- **小さいタスクは小さいモデルに向く**。入力はそのタスクに要る材料だけ（プロファイル全体を渡さない）、出力は数フィールド。12B でも enum から選ぶだけなら外しにくい。
- **失敗が局所化する**。一括生成では「引数なしで溢れる」の直し方がグラフ全体の書き直しになり、別の場所を壊した。段階化すれば `decide-output` の `limit` だけを直せる。
- **式を混ぜない**。グラフのプロンプトに式の文法を足すと、どちらの品質も落ちる。式には既に専用の検証つき経路がある。
- **説明文を決定的に作れる**。引数の形式・実在値の例・データの範囲・既定の粒度は仕様とプロファイルから機械的に書ける。エージェントが「2015年12月31日」のような存在しない時点を渡す原因（説明不足）を構造的に減らせる。

## 検討した代替案

- **正規化を増やし続ける**: 後追いで、機能追加のたびに負債が増える。正規化はフォールバック経路のために残すが、主経路にはしない。
- **より大きいモデルを前提にする**: ローカル LLM で回せることがこの製品の前提。小さいモデルで安定する設計は、大きいモデルでも安くて速い。
- **1 回のプロンプトで `ToolSpec` 全体を書かせる**: グラフよりは良いが、結合・絞り込み・計算・出力の判断材料が混ざり、入力が大きくなる。差し戻しも全体のやり直しになる。
- **式を `decide-computations` に書かせる**: 文法・関数表・検証・修復を二重に持つことになる。
- **コンパイラを持たず、タスクごとにグラフの断片を書かせて繋ぐ**: 断片の接続（ポート・列名の衝突）でまた機械的な間違いが出る。

## 結果・影響

- 表現できる Tool の形は `ToolSpec` の語彙に限られる（集計ノードなどは一括経路へフォールバックする）。語彙を足すときはコンパイラと検証に足す。
- Tool 1 本あたりのモデル呼び出しは 1 回（＋修復）から 3〜5 回（小）に増える。1 回が短く、やり直しが局所的なので、12B での実測では総時間が減ることを期待する（実機確認の結果は ADR-0047 の追記と本 ADR の追補に残す）。
- `maxRoleCalls` の会計はタスクごとに数える。
- Analyst の `add-tool` 提案は当面、従来の一括 ToolSmith を使う。

## 実装メモ（2026-09-20）

決定そのものは変えていない。実装で確定させた点だけを挙げる（詳細は [implementation/v42 §10](../../implementation/v42-staged-tool-generation.md)）。

- **決定 4 の「式が作れない計算列はその列だけ落とす」** は、式提案ユースケースの**内部の1回の差し戻し**だけで判断する。外側からもう一度同じプロンプトで頼み直しても往復が増えるだけなので、辞退・検証失敗・モデル失敗はいずれも即座にその列を落とし、理由を `tool_generated` の message に残す。
- **決定 5 の差し戻し先**のうち、形・スキーマ伝播・証拠列の欠落は**どのタスクの決定でもない**（コンパイラのバグ）ので差し戻さずに失敗させ、一括経路へフォールバックする。単体テストで防ぐ側の問題として扱う。
- **粒度を引数にしたToolには「引数なしの呼び出し」が存在しない**（必須引数）。既定呼び出しの溢れガードは「必須引数だけを設計時サンプルで埋めた呼び出し」で見るように広げた。
