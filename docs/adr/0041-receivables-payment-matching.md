# ADR-0041: 入金消込の 2 段階判定・請求書の税率別端数処理・仕訳下書きへのポート連携

- Status: Accepted（2026-09-15 に R1 を実装。実装で決めた細部は docs/22 §16）
- Date: 2026-09-14
- 関連: [docs/22-receivables.md](../22-receivables.md) / [ADR-0038](./0038-journal-two-stage-judgment.md)（仕訳の 2 段階判定）/ [ADR-0035](./0035-domain-shared-kernel-and-boundary-conversion.md) / [ADR-0039](./0039-business-feature-registration.md)（業務の登録点）/ [docs/21-expense.md §2.8](../21-expense.md)（仕訳 BC との依存の向き）

## 文脈

請求書を発行し、銀行明細の入金を請求に消し込む業務テンプレートを足す。既存の会計・請求ソフトの消込機能には、設計が大きく分かれる点が 4 つある。

1. **どこまで自動で確定するか**。入金額と請求額が一致しても、同額の請求が複数ある・名義が違う・振込手数料が引かれている・複数の請求をまとめて払われる、が日常的に起きる。「計算上一意なら自動確定」にすると、手数料と偶然同額の差額や、同じ合計になる別の組み合わせを黙って確定し、売掛金の残高が実態とずれる。逆に全件を手作業にすると機能の意味が無い。
2. **振込名義をどう照合するか**。銀行の振込依頼人名は半角カナ・小書き無し・法人略語（`ｶ)` `ﾕ)` `ﾄﾞ)`）・30 桁前後での切り詰めが入り、取引先マスタの漢字の社名とは一致しない。漢字 → カナの変換辞書や LLM による推定は、外れたときに誤った取引先へ消し込む。
3. **合算入金の組み合わせ探索**。未入金請求が n 件ある取引先の部分集合は 2^n あり、上限を置かないと 1 回の判定がリクエストを塞ぐ。
4. **消費税の端数処理**。適格請求書では「1 請求書につき税率ごとに 1 回」（国税庁 Q&A 問 57）。明細ごとに丸めて合算する実装は税額が数円ずれ、記載事項の要件を満たさない。外部の見積・注文データから請求書案を作ると、この違反が持ち込まれる。

さらに、発行と消込は売上・入金の仕訳を生むが、仕訳 BC は別の作業者が変更中で、請求側の都合で仕訳のコードを書き換えにくい。

## 決定

### 1. 消込は 2 段階。`decided` は「同額 + 名義一致 + 候補 1 件」だけ、確定は常に人が押す

判定 `judgeTransaction` は**入金・未入金請求・取引先・設定だけを引数に取る純関数**にし、結果を `decided` / `candidate`（候補付き保留）/ `unmatched`（保留）と**理由コード 1 つ**で返す（docs/22 §4）。確定できないことはエラーではなく結果である（ADR-0038 決定 1 と同じ）。

- `decided` は「入金額 = 請求残高」かつ「名義が別名 / カナ / 社名で完全一致」かつ「その候補がちょうど 1 件」に限る。
- 手数料差額・合算・一部入金・名義の部分一致・金額だけの一致は、計算上一意でも `candidate` に留める。
- **確定は画面から人が押す**。`decided` にも「一括確定」ボタンを置くが、自動では確定しない。エージェント用ツールは候補と理由を読むだけで、確定・名義の学習・仕訳の作成をしない（docs/20 §14.1 と同じ理由: 状態を変える操作は承認ゲートと「誰がいつ確定したか」が要る）。
- 評価順は固定し、最初に当たった理由を 1 つだけ返す。理由を並べると画面の「次の一手」が定まらない。

### 2. 名義照合は決定的な正規化 + 取引先ごとの別名。別名は人の確定時にだけ増える

`normalizePayerName` は NFKC・半角カナ → 全角・法人略語の除去（全銀の略語体系を定数で持つ）・小書き → 並字・長音と記号の揺れの吸収・空白除去を行う純関数で、摘要側とマスタ側の**両方に同じ関数を通して**比較する。漢字 → カナの推測はしない。

取引先は `kana` と `payerAliases[]` を持ち、別名は利用者が一覧で編集・削除できる。別名が増える経路は (a) 利用者の手入力、(b) **消込の確定時に「この名義を覚える」を選んだとき**、の 2 つだけ。取消時には、その確定で学習した別名の削除を提案する。同じ正規化名が複数の取引先に登録されたら、どちらにも寄せず `alias-conflict` として保留し、修正先へ導線を張る。

LLM による名義推定は MVP に入れない。入れるときも候補の並べ替えにだけ使い、`decided` の条件には使わない。

### 3. 合算探索は 1 取引先内に限り、計算量の上限をコード定数で固定する

合算の組み合わせは**名義で絞れた取引先ごと**にだけ探し、名義が一致しない入金では探さない（全取引先の組み合わせは偶然の一致が多く、誤誘導の方が大きい）。探索は期日の古い順に最大 20 件、組み合わせの大きさ 2〜K（利用者設定、上限 5）、評価数 50,000 で打ち切り、6 組目の一致で停止する。打ち切ったことは `search-limit` という理由として見せ、手動配分へ導く。

利用者が変えられるのは K・手数料の許容範囲などの**業務上の値**で、計算量の安全上限（20 / 5 / 50,000）はコード定数にする。設定値が上限を超えたら丸めずに拒否する。

### 4. 税額は「請求書 × 税率ごとに 1 回」を整数演算で計算し、発行する値は常に計算値にする

税率ごとに明細金額を合算してから、丸めモード（切り捨て / 四捨五入 / 切り上げ。利用者設定）で 1 回だけ丸める。計算は整数演算だけで行い、浮動小数を使わない。請求書の `totals` は保存のたびにドメインが再計算し、クライアントや取込元の申告値を採らない。

外部から持ち込んだ下書き（ツールの請求書案・JSON 貼付）の申告税額は `declared` として検査にだけ使い、明細ごとに丸めた合計と一致すれば `per-line-rounding` 違反として発行を止める。値の自動補正はせず、差額を示して「計算値で置き換える」を人が押す（仕訳の抽出整合チェックと同じ方針）。発行時に発行者情報・取引先名・丸めモードを請求書へ写して凍結し、以後の設定変更で発行済みの内容が変わらないようにする。

### 5. 仕訳とはポート `JournalDraftSink` で繋ぎ、作るのは下書きだけ。確定済みの仕訳は上書きしない

receivables の application 層に `JournalDraftSink`（`upsertDraft` / `discardDraft` / `checkAccounts` / `taxRateOf`）を定義し、`src/composition/receivables.ts` が仕訳の既存ユースケース（`SaveJournalEntryUseCase` / `DeleteJournalEntryUseCase` と科目マスタの読み取り）を包んで注入する。receivables の application は仕訳の application を import しない。依存は receivables → journal の一方向で、domain から使うのは仕訳 domain の純関数と値型（正規化・CSV・プリセット）だけにする（経費精算 docs/21 §2.8 と同じ規律）。

- 発行で売上、消込の確定で入金（手数料差額は支払手数料）の仕訳を**下書き**で作る。科目 id・税区分コードは利用者設定で、仕訳の科目マスタを id で参照する。
- アダプタは書く前に既存の仕訳の状態を読み、`draft` 以外（利用者が確認した / 出力した仕訳）なら**書かずに**「仕訳側で直してください」を返す。`SaveJournalEntryUseCase` は既存 id の更新で状態を保ったまま中身を差し替えるため、この確認をアダプタの責務にする。
- 発行・確定と仕訳の下書きは同じ SQLite 接続上の `UnitOfWork` で 1 トランザクションにする。科目が無ければ発行・確定ごと巻き戻し、「発行済みなのに仕訳が無い」状態を作らない。
- 仕訳側に必須の変更は無い。仕訳の出所を示す専用の値（`decidedBy`）が無いので、MVP はタグ（`receivables:invoice:<id>` など）で出所を示す。

### 6. 銀行明細 CSV は列マッピングを保存して再利用し、重複はフィンガープリントで検出する

仕訳の銀行プリセットと列マッピング（`rowToDocument` / `rowToDocumentWithMapping`）を行の正規化に再利用し、その上に**保存できる列マッピング**（ヘッダ行の位置・振込依頼人名の列・口座の既定を含む）を足す。列名署名が一致すれば次回から自動で選ぶ。文字コードはサーバーで判定する（BOM → 厳格な UTF-8 → CP932）。文字コードの判定は Node 標準の `TextDecoder`（`shift_jis` は Windows-31J 相当で NEC 特殊文字も読める）で行い、依存を増やさない。重複取込は口座・日付・金額・正規化名義・残高・同一ファイル内の出現順から作るフィンガープリントの一意索引で検出し、スキップした行は理由付きで返して利用者が取り込ませることもできるようにする。

### 7. 請求書の見た目はブラウザの印刷用レイアウト。PDF 生成・送付はしない

印刷用レイアウトを UI の画面として持ち、`@media print` とブラウザの「PDF に保存」で出力する。サーバーに PDF ライブラリを持ち込まない（ADR-0038 決定 3 と同じ理由）。メール送付は SMTP 資格情報（秘密値）の管理が要るので別の決定に回す。

## 検討した代替案

- **計算上一意なら自動確定**: 手数料差額と偶然同じ差額の別請求や、同じ合計の別の組み合わせを黙って確定する。売掛金の残高が実態とずれ、発見が遅れる。確定 1 クリックの手間より、誤消込を後から探すコストの方が大きい。
- **判定から確定までツールで行えるようにする**: 確定は売掛金と仕訳を変える。read-only のツールでは済まず承認ゲートが要るうえ、画面で見ている状態と帳簿の実体がずれる。候補の参照までに留める。
- **LLM に名義と取引先を推定させる**: 外れたときの誤消込が見えにくく、同じ入金が実行ごとに違う取引先になり得る。決定的な正規化と人が確定した別名の学習で、使うほど `decided` が増える形を選ぶ（ADR-0038 の「LLM はルールを作る側に置く」と同じ考え方）。
- **漢字社名 → カナの辞書変換**: 読みが一意でない社名が多く、辞書の保守も要る。取引先に振込名義カナを持たせる方が確実。
- **合算を全取引先で探す / 上限なしで探す**: 偶然の一致が増えるうえ、計算量が請求件数に対して指数的に増える。
- **合算を部分和の動的計画法で解く**: 金額が大きい（円単位で数百万）ため表が大きく、「一意か」を知るための組み合わせの列挙も要る。件数を 20 に絞った深さ優先の方が単純で、上限の説明もしやすい。
- **明細ごとに丸めて合計する**: 実装は簡単だが、適格請求書の端数処理の要件（Q&A 問 57）に反する。
- **申告された税額との差を自動補正する**: どちらが正しいか（明細の読み違いか、丸めの違いか）は人にしか分からない。補正すると誤読がそのまま請求額になる。
- **仕訳のユースケースを receivables の application から直接呼ぶ / 仕訳テーブルへ直接書く**: 仕訳 BC の内部（科目名の写し・貸借一致の検証・状態の規律）を二重に持つか迂回することになる。ポートにしておけば、仕訳側の変更は composition のアダプタ 1 か所で吸収できる。
- **仕訳側に「請求連携」用の新しいユースケースを足してもらう**: 仕訳のコードは並行して変更中で、既存のユースケースで足りる。必要になった時点で「仕訳側への変更要求」として出す。
- **サーバーで PDF を生成する**: ネイティブ依存とフォントの手当てが増える。ブラウザの印刷で足りる。

## 帰結

- 判定・名義正規化・合算探索・税計算がすべて純関数なので、境界（手数料の上下限ちょうど、組み合わせの一意 / 複数、探索の打ち切り、丸めモード × 税抜 / 税込）を表形式のテストで固定できる。
- 使い始めは漢字の取引先名が振込名義と一致しないため、ほとんどの入金が `amount-only` か `no-candidate` になる。「確定して名義を覚える」が主経路で、同じ取引先の 2 回目以降が `decided` になる。取引先登録時に振込名義カナの入力を促す。
- `decided` も人の確定が要るので、件数が多いワークスペースでは「決定を一括確定」の操作が必須になる。
- 仕訳下書きはタグでしか出所を示せない。仕訳画面から請求書へ戻る導線は、仕訳側が対応するまで無い（docs/22 §14 の任意の変更要求）。
- 同じ銀行明細を仕訳の取込にも入れると、入金が二重に仕訳される恐れがある。receivables の明細取込画面と仕訳の取込画面の両方で注意を出し、仕訳側での検出は任意の変更要求に回す。
- 確定済みの仕訳がある請求・消込を取り消しても、仕訳は残る。取消の仕訳は利用者が仕訳側で作る（画面は該当の仕訳を開くボタンを出す）。
- 過入金（前受金 / 返金）は `overpayment` として保留に留まり、入金消込の中では解決できない。
- SQLite のスキーマは version 7（`receivables_*` の追加のみ。既存データはそのまま）。
