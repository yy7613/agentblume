# ADR-0045: 関数電卓ノード（`calculate`）— 数式で計算列を足す

- Status: Accepted
- Date: 2026-09-19
- 関連: [docs/06-etl-tool-builder.md §2.2 / §3.14](../06-etl-tool-builder.md) / [implementation/v39-calculate-node.md](../../implementation/v39-calculate-node.md) / [ADR-0028](./0028-structured-node-configuration-ui.md)（構造化設定 UI）/ [ADR-0044](./0044-ai-judge-node.md)（決定的計算と LLM の境界）/ [ADR-0015](./0015-etl-transform-expansion.md)（変換ノードの拡張）

## 文脈

Tool Builder の変換ノードは `select` / `rename` / `cast` / `filter` のように**列を選ぶ・名を変える・型を変える・行を絞る**ことはできるが、**列の値から新しい値を計算する**手段が無い。`docs/06 §2.2` には「計算列（式エディタ）」が v16 以降の予定として残っている。利用者からの要望は「税込金額 = 金額 × 1.1」「単価 = 金額 ÷ 数量」「対数変換」「角度の変換」のような、表計算ソフトのセルに書く程度の式である。

制約は 3 つ。

1. **`EtlNode` は同期・純粋関数**であり、`execute` は決定的でなければならない（[ADR-0044](./0044-ai-judge-node.md) の原則。計算は LLM にさせない）。
2. **式は保存され、後で実行される**。`eval` や `new Function` のように任意コードを実行する手段は使えない（保存済み Tool は他の利用者・エージェントが実行する）。
3. **ノーコードの利用者が式を書く**。演算子や関数名を覚えずに組める UI が要る。一方で UI 層は domain を import しない規律（依存検査）があるため、関数一覧を UI と domain の両方が持つ必要がある。

## 決定

### 1. 汎用の変換ノード `calculate` を 1 つ足す。業務ノードではない

`calculate`（kind: transform / arity: 1）は、入力の各行について**数式を 1 つ評価し、結果を 1 列**として足す（同名の列があれば置き換える）。業務（仕訳・経費…）に属さない汎用機能なので、[ADR-0039](./0039-business-feature-registration.md) の業務登録点ではなく、`cast` と同じ並び（`nodes/index.ts` に直接 register、`node-catalog.ts` に直接掲載）に置く。

### 2. 式は自作の小さな解釈器で読む。`eval` は使わない

数式は domain の `calculate-expression.ts` が字句解析 → 構文解析（再帰下降）→ 評価する。受け付けるのは**数値・列参照・算術演算子・括弧・固定の関数群・定数**だけで、比較・条件分岐・文字列・代入・利用者定義関数は受け付けない。条件による分岐は `filter` / `ai-judge` の責務であり、ここへ持ち込まない（Tool Builder に制御構造を混ぜないという [06 §1](../06-etl-tool-builder.md#1-ノード分類の全体像) の境界を守る）。

式の長さ・入れ子の深さ・トークン数に上限を置き、超えたら `ConfigError` で止める。悪意ある式で解釈器を疲弊させないため。

### 3. 列は `[列名]` で参照する。裸の識別子は列名に一致するときだけ列として扱う

`[金額]` のように角括弧で囲めばどんな列名でも参照できる（日本語・空白・記号を含む列名のため）。英数字だけの列名は裸で書いてもよいが、**関数名・定数名と衝突しない、かつ入力スキーマに存在する**ときだけ列として解釈し、それ以外の裸の識別子は「未知の名前」として `inferSchema` の error にする。黙って 0 や null にはしない（打ち間違いを実行前に見せる）。

### 4. 型は `number` に限り、評価不能は既定で null、指定で失敗

参照する列は `number` 型を前提とする。`string` / `unknown` / `null` 型の列は実行時に数値へ寄せる（数値文字列だけ通し、他は null）が、`inferSchema` で warning を出す。`boolean` / `date` も同様に warning（実行時は null）。

評価結果が有限の数でない（0 除算・負の平方根・`ln(0)` など）とき、および参照列が null のときの扱いは `onError` で選ぶ。既定の `'null'` は結果を null にして行を残す（`cast` の「変換不能 → null」と同じ規律）。`'fail'` は `SchemaError` で実行を止め、行番号・式・理由を添える（「なぜ落ちたか」を利用者が直せる形で返す）。

出力列は `{ name: outputColumn, type: 'number', nullable: true }`。null の可能性は消せないので常に nullable。`precision` を指定すると小数第 n 位で四捨五入する（浮動小数の誤差は避けられないため、通貨の丁寧な丸めが要る場合は後段の `cast` や表示側で扱うことを文書に書く）。

### 5. UI は関数電卓の見た目にし、関数一覧は表示用の写しを持って domain とピン留めする

設定ダイアログに、数字・演算子・括弧のキーパッド、関数ボタン（基本 / 丸め / 指数・対数 / 三角 の 4 群）、入力列のチップ（押すと `[列名]` を挿入。`number` 型を前に出し、他の型は注記付きで薄く出す）、式の表示欄（直接編集もできる）を置く。押した位置に挿入し、`×` `÷` の表示は保存時に `*` `/` へ写す。

UI 層は domain を import しない規律なので、関数の一覧（名前・引数の数・群）は UI 側にも表示用の写しを持ち、**テストが domain の正典と一致をピン留めする**（`filter` の演算子一覧と同じやり方。`NodeInspector.group-limit-filter.test.tsx` 参照）。式の妥当性検査は UI で二重実装せず、`inferSchema` の issue（サーバー側）をそのまま表示する。UI が自前で見るのは括弧の対応だけ（打っている途中の手掛かりとして）。

## 検討した代替案

- **`eval` / `new Function` / 既存の式ライブラリ（mathjs 等）を使う**: `eval` 系は任意コード実行そのものであり保存済み Tool の実行経路に置けない。mathjs は依存を 1 つ増やしたうえ、代入・行列・文字列・条件など今回受け付けたくない機能を丸ごと持ち込み、「受け付けない」を保証するのに結局ラッパが要る。受け付ける文法が小さいので自作の方が境界を明示できる。
- **`filter` のように条件式もこのノードで扱う**: 比較や `if` を足すと、Tool Builder に制御構造が入り込み、`ai-judge` → `filter` で分岐を表現するという既存の整理（[ADR-0044](./0044-ai-judge-node.md) 決定 2）と二重になる。計算に絞る。
- **列参照を裸の識別子だけにする**: 日本語や空白を含む列名を参照できない。角括弧を正とし、裸は英数字の列に限る。
- **評価不能を常に失敗にする**: 1 行の 0 除算で数千行の計算が止まり、`cast` の規律（変換不能は null）とも揺れる。既定は null、必要なら `'fail'` を選べる形にした。
- **UI で式を評価してその場で結果を見せる**: 評価器を UI にも持つことになり二重実装になる。既存のプレビューパネル（サーバーが実グラフを実行）が同じ役目を果たすので、UI は式を組む道具に留める。

## 結果・影響

- `docs/06 §2.2` の「計算列（式エディタ）」は本ノードで実装済みになる。
- 新規ノードのため保存データ形式に破壊的変更はない。
- 関数一覧を増やすときは domain の正典（`CALCULATE_FUNCTIONS`）と UI の写しの両方を直す。片方だけ直すとピン留めテストが落ちるので、漏れは検査で捕まる。
- エージェント引数（`agent-input`）を式の中で参照する束縛は本 ADR の範囲外。要望があれば `filter` の `valueBinding` と同じ形で足す。
