# ADR-0042: 契約書レビューを「本文テキスト + 決定的な判定 + 利用者が持つ審査基準」で組む

- Status: Accepted（2026-09-15 実装）
- Date: 2026-09-14
- 関連: [docs/23-contract.md](../23-contract.md) / [ADR-0038](./0038-journal-two-stage-judgment.md)（仕訳の 2 段階判定）/ [ADR-0039](./0039-business-feature-registration.md)（業務を業務別ファイルだけで足す登録点）/ [ADR-0034](./0034-domain-primitive-tiers-and-id-types.md)

## 文脈

受け取った契約書を自社の審査基準（プレイブック）でレビューし、要交渉の条項に修正文案を添え、締結後は更新・解約通知の期限を管理する業務テンプレートを足す。仕訳と同じく LLM を使うが、次の点で仕訳より難しい。

1. **入力が長く、形がまちまち**。業務委託契約は 10〜30 ページで、テキスト層のある PDF・スキャン PDF・写真・貼り付けテキストのどれでも届く。既存の添付経路は画像前提（`ImageAttachment` = name + dataUrl、チャットは 2 枚まで、抽出は 4 枚まで）で、既定のローカル 12B 級モデルは vision で 1 ページ 17〜19 秒かかり、文脈長も 8k〜16k 程度しかない。契約書 1 通をまるごと 1 回で読ませる設計は、速度でも文脈長でも成り立たない。
2. **判定の根拠が問われる**。「要交渉」と言われた担当者は、どの条文のどの文言がどの基準に反するのかを確かめてから相手方に出す。LLM が言い換えた条文や存在しない条文を根拠にすると、交渉の場で恥をかく。
3. **審査基準は会社ごと・立場ごとに違う**。発注側と受注側で損害賠償の上限に対する評価は正反対になり、支払期日の許容日数や管轄裁判所も会社で違う。条項の種類や基準を列挙型でコードに持つと、基準 1 つの変更に再デプロイが要る。
4. **法令・税に触れる**。支払期日 60 日（下請法改正後の取適法、フリーランス法）や印紙税の課税文書（第 2 号・第 7 号）は、条文を読めば機械的に照合できる部分と、相手方の規模・契約の実質など条文の外の事実で決まる部分が混ざる。ここを LLM に「判断」させると、法的助言のような出力が根拠なく出てしまう。
5. **期限は 1 日ずれると意味が無い**。「満了の 3 か月前まで」は月末・うるう年で結果が変わり、自動更新で毎年動く。LLM が日付を計算すると、同じ契約で実行ごとに期限が変わりうる。

## 決定

### 1. 入力はすべて「ページ境界付きの本文テキスト 1 本」へ揃え、vision は文字起こしだけに使う

テキスト貼り付け・PDF のテキスト層（ブラウザで `pdfjs-dist` により全ページ抽出）・画像とスキャン PDF（ページごとに vision で文字起こし、利用者が確認）の 3 系統を、取込の時点で本文テキストに変換して保存する。条項抽出・判定・期限計算・検索はテキストだけを見る。

vision の遅さはページ数に比例する 1 回きりの費用に閉じ込め、繰り返し走る条項抽出と再レビューは速いテキスト処理にする。PDF の処理はブラウザ側に置き、サーバーに PDF ライブラリを持ち込まない（ADR-0038 §3 を継承）。PDF や画像の原本は保存しない（本文テキストとハッシュだけを持つ）。

### 2. 条文は決定的に分割し、LLM は条文束ごとに「値と引用」だけを返す。引用は本文と照合する

`第N条` の見出しで条文を分け（検出できなければ段落）、トピックごとのキーワードで候補条文を絞り、`chunkMaxChars`（既定 4,000 文字）以内の束ごとに構造化出力で抽出する。出力は必ず `articleRef` と本文からの逐語の `quote` を持つ。

後処理で引用を本文（NFKC・空白無視）と照合し、見つからなければ値は残したまま `quote-not-found` として判定を `unresolved` にする。束の失敗は抽出全体を失敗にせず、そのトピックだけ `extraction-failed` にする。仕訳と同じく**値は補正しない**。

### 3. 条項の種類・基準・推奨文案・法令の設定値・印紙税の表はプレイブック（データ）に置き、コードには「型・演算子・理由コード・計算規則」だけを置く

トピック（`id` / `label` / `keywords` / `guidance`）と基準（`required` / `condition` / `legal` / `llm` の 4 種の検査と、`onFail` / `recommendedText` / `rationale`）はワークスペース単位のデータで、同梱テンプレートは初期値に過ぎない。コードの列挙は値の型（`valueKind`: 期間・自動更新・通知・支払条件・賠償上限・許諾・知財帰属・管轄・自由記述）と比較演算子と理由コードだけにする。これで「基準を足す・日数を変える・管轄を自社所在地にする」は画面の編集で済み、判定器は型ごとに決定的に書ける。

### 4. 判定は純関数で決め、LLM には「はい / いいえ / 判断不能」と引用だけを答えさせる

`reviewContract(document, playbook, llmAnswers, today)` を純関数にする。評価順は「立場 → 条項の有無 → 抽出の信頼性 → 法令の照合 → 決定的な条件 → LLM 基準の回答の適用」、トピックの判定は `reject > negotiate > unresolved > accept` の最悪値。LLM 基準の呼び出しは application が先に行い、回答（`answer` と条文内に実在する `evidenceQuote`）を純関数へ渡す。根拠が条文に無い回答は採らない。

判定できないことはエラーではなく**結果**（`unresolved` + 理由コード）で返し、理由コードごとに「原因・次にやる操作・その場所を開くボタン」を UI が出す（ADR-0038 §1 と同じ考え方）。モデルが使えなくても決定的な基準は判定して返す。

### 5. 法令・税は「設定値との照合」と「候補の提示」に留め、条文外の事実は人に申告させる

支払期日は支払条件から最長日数を暦で計算し（受領日を 1 日目と数える。取適法・フリーランス法の「受領日から起算して 60 日」と同じ数え方）、設定値（初期値 60 日）と比べる。相手方が取適法・フリーランス法の対象かは利用者が取込時に選び、未入力なら照合を確定しない（`counterparty-profile-missing`）。印紙税は契約の性質と金額から課税文書の**候補**を `info` で出すだけで判定には影響させず、電子契約なら不要とされる旨に置き換える。日数・禁止支払手段・税額表はすべて設定値で、画面・API・ツール説明に「法的な判断ではなく登録された基準との照合」と明記する。

### 6. 期限は暦の規則を持つ純関数で計算し、本文の日付表現と突き合わせる

満了日（応当日の前日、応当日が無ければ月末）、「満了の N か月前まで」（同日、無ければ月末、月末は月末へ写す）、自動更新（満了翌日から同じ規則）、表示時の現在期の決定を `deadline.ts` に置き、境界を表形式のテストで固定する。抽出値と引用内の日付・期間表現が合わなければ `deadline-mismatch` の警告を出す（仕訳の「税率別合計 ≠ 総額」に相当）。営業日や「N か月前の月末」などの変形は MVP では計算せず、手入力を求める。

### 7. エージェントからは参照だけ。確定・締結登録・期限の完了は画面から人が押す

組込みツールは `contract_review_draft`（添付の契約書を条項分解してプレイブックで判定。保存しない）、`contract_deadlines`（期限が近い契約）、`contract_clauses`（締結済み契約の条項検索）の 3 本で、すべて `read-only`。仕訳 docs/20 §14.1 と同じ理由で、レビューの確定・締結登録・期限の完了はツールにしない。

長文の契約書を添付からツールへ渡すには画像添付では足りない。**テキスト添付**（ブラウザで PDF から抽出した本文）を実行文脈に足し、画像と同じく `NodeContext` → `ResolveDataSourceGraphUseCase` の経路で source ノードへ流す。行ソースの要件には「画像かテキストのどちらか 1 件以上」（`attachments-or-documents`）を足し、画像必須の既存の要件（仕訳の帳票読み取り）は変えない。モデルへの user メッセージには本文を載せず「添付: ファイル名・ページ数・文字数」の短い目印だけを入れる（12B の文脈を契約書本文で埋めない）。子エージェントと再開実行には渡さない既存の規律はそのまま守る。

### 8. 保存は SQLite v8、`record_json` + 絞り込み列。期限は投影テーブルに出す

`contract_playbooks` / `contract_documents` / `contract_reviews` / `contract_signed_contracts` / `contract_deadlines` を `src/adapters/storage/contract-migrations.ts`（version 8）で足す。正本は各集約の `record_json` で、期限は締結済み契約の保存と同じトランザクションで `contract_deadlines` へ投影し、期限の近い順の一覧と `contract_deadlines` ツールを索引で引く。本文は 300,000 文字、1 レコード 8 MiB を上限にする。

## 検討した代替案

- **契約書を丸ごと 1 回で LLM にレビューさせる**: 実装は最小だが、12B 級の文脈長を超え、30 ページで数分〜十数分かかる。根拠の位置が取れず、同じ契約でも実行ごとに結論が変わる。
- **全ページを vision で読んだまま条項抽出まで行う**: ページ画像を毎回送るので再抽出・再レビューのたびに 1 ページ 17〜19 秒の費用が再発する。テキスト層のある PDF では純粋な無駄になる。
- **サーバー側で PDF を解析する**: ネイティブ依存とサンドボックスの手当てが増える（ADR-0038 と同じ理由で退ける）。
- **条項の種類と基準を列挙型・固定表でコードに持つ**: 型で守れるが、会社ごと・立場ごとの基準の違いに応えられず、基準 1 つに再デプロイが要る。利用者指示「基準は利用者が編集」にも反する。
- **LLM に受け入れ可 / 要交渉 / 不可を直接答えさせる**: 判定理由が基準と結び付かず、基準を直しても結果が追従しない。合否の境界（日数・金額）を LLM が数え間違える。
- **LLM に期限の日付を計算させる**: 月末・うるう年で誤り、実行ごとに揺れる。期限台帳の目的に反する。
- **取適法・フリーランス法の適用可否を資本金・従業員数から自動判定する**: 相手方の規模は契約書に書いていないことが多く、推定すると法的判断を装った誤りになる。利用者の申告に留める。
- **PDF を画像にしてチャット添付（画像 2 枚）で渡す**: 2 ページまでしか渡せず、契約書では役に立たない。
- **契約書本文を user メッセージにそのまま載せてツールにも渡す**: モデルの文脈を本文で使い切り、ツールの結果を読む余地が無くなる。

## 帰結

- 判定・期限計算・印紙税候補・突き合わせが純関数なので、回帰テストにモデルもデータベースも要らない。LLM はフェイクの応答で抽出と基準回答の経路だけを試験できる。
- 引用照合があるため、モデルの言い換えは必ず `unresolved` として人に見える。その分、小さいモデルほど `quote-not-found` が増え、人の確認の手間が増える（実測して §13 のリスクに反映する）。
- キーワード絞り込みで速度を得る代わりに、見出しや語が特殊な契約では条項を見落とす。`clause-missing` に「全条文を読ませる」導線を必ず付ける。
- プレイブックが利用者データなので、基準を壊すと判定が一斉に `unknown-topic` / `field-missing` になる。保存時に基準のパスと置換子を検証し、Review には判定時のプレイブックの写しを残す。
- 法令の日数・印紙税の表は改正で古くなる。初期値である旨と出典を画面に出し、更新は利用者の責務とする（コードの改修は不要）。
- テキスト添付の追加は共通部（実行 API のスキーマ、`run-agent-preview`、`ResolveGraphContext`、チャット画面）への変更を伴う。画像添付の形は変えないので仕訳のツールには影響しない。ADR-0039 の登録点がこの経路を持たない場合は、共通部への変更として別途合意が要る。
- SQLite のスキーマは version 8（`contract_*` の追加のみ。既存データはそのまま）。PDF・画像の原本は保存しないので、原本の保管は利用者の文書管理に委ねる。
- 実装で設計から変えた点（受領日の数え方・契約金額の入力・行ソースの要件の分け方・`run-routes.ts` への 2 行など）は docs/23 §14 に記録した。
