# ADR-0038: 仕訳の 2 段階判定・利用者が持つ科目体系・汎用 CSV

- Status: Accepted
- Date: 2026-09-13
- 関連: [docs/20-journal.md](../20-journal.md) / [docs/04-api-spec.md §3.4](../04-api-spec.md#34-仕訳journal) / [ADR-0034](./0034-domain-primitives.md) / [ADR-0035](./0035-shared-validation-helpers.md)

## 文脈

伝票・帳票（請求書・レシート・銀行明細 CSV・カード明細）から仕訳を起こす機能を入れる。既存の会計ソフト（freee / マネーフォワード / 弥生）はいずれも「自動仕訳ルール」を持つが、次の 3 つは製品ごとに設計が大きく分かれる。

1. **確定できないときにどうするか**。ルールに当たらない伝票は必ず出る（初めての取引先、目的で科目が変わる飲食代、1 品 10 万円の境界）。ルール照合だけの設計では、当たらなかった伝票が「未処理」の山になり、利用者は何をすればよいか分からない。逆に LLM に毎回仕訳を作らせる設計は、同じ取引が実行のたびに違う科目になり、帳簿として使えない。
2. **勘定科目・税区分をコードに持つか**。青色申告決算書の科目を列挙すれば大半は足りるが、業種ごとの科目（作業用消耗品費・支払手数料の細分）と補助科目・部門は利用者ごとに違う。列挙型で持つと、科目を 1 つ足すためにコード変更と再デプロイが要る。
3. **PDF をどこで画像にするか**。証憑の多くは PDF で届く。vision モデルへ渡すにはページを画像化する必要がある。

さらに出力先の会計ソフトは複数あり、列の並びも項目名も違う（弥生 25 項目 / freee / MF）。最初からどれか 1 社に寄せると、他社向けは全部書き直しになる。

## 決定

### 1. 判定を 2 段階に分け、Stage 1 を純粋関数にする

**Stage 1**（決定的）: 有効なルールを scope と conditions で照合し、一意に確定できれば仕訳ドラフトを作る。**Stage 2**（LLM ヒアリング）: 確定できなかった伝票について、その理由（該当ルール無し / 複数ルール競合 / 必要項目不足 / 「迷うケース」該当 / suggest モード）を示し、質問 → 回答 → **新しいルールの提案** → 利用者の確認 → 登録 → 再判定 という流れに乗せる。

Stage 1（`src/domain/journal/judgment.ts` の `judgeDocument`）は **facts・ルール・科目マスタ・時刻だけを引数に取る純粋関数**にする。I/O もモデル呼び出しも持たないので、同じ入力からは必ず同じ仕訳が出る。これが「帳簿として使える」ことの土台であり、テストも表形式で書ける。

確定できなかったことは**エラーではなく結果**（`undecided` + 理由コード）として返す。理由コードは UI が「原因 → 次の一手 → 修正場所へのボタン」を出すための情報で、`no-rule` はヒアリング開始へ、`multiple-rules` はルール一覧の優先度調整へ、`missing-fact` は帳票の項目編集へ、`unknown-account` は科目マスタへ導線を張る。

LLM が作るのは**ルール**であって仕訳そのものではない。同じ取引が次回から決定的に処理されるので、使うほど Stage 1 の通過率が上がり、LLM 呼び出しは減っていく。

### 2. 科目体系はワークスペースのデータにし、ルールは科目を id で参照する

勘定科目・税区分・補助軸（補助科目 / 部門 / …）を `ChartOfAccounts` 集約としてワークスペース単位で保存する。**コードに勘定科目や税区分の列挙型を持たない**（`src/domain/journal/default-chart.ts` の標準セットは初期値に過ぎず、ここ以外に科目名がハードコードされる場所は無い）。追加・改名・無効化・並び替え・CSV 取込 / 出力ができる。

ルールと仕訳は科目を **id** で参照する。名称変更に自動で追従し、削除は論理削除（`enabled: false`）にして参照を壊さない。消えた / 無効化された科目を指すルールは判定時に `unknown-account` として検出され、修正導線が出る。仕訳の各行は id に加えて**確定時の科目名**を写して持つので、後からマスタを改名しても過去の仕訳は当時の名前を保つ。

科目マスタを保存したことが無いワークスペースでは、参照時に標準セットを返すが**保存はしない**。参照が書き込みを起こすと、読み取り権限しか無い利用者が失敗し、標準セットを後から改善しても一度画面を開いたワークスペースには古い seed が焼き付く。

### 3. PDF はブラウザ側で画像化し、サーバーに PDF 依存を持ち込まない

PDF のページ画像化は UI で `pdfjs-dist` を使って行い、サーバーへは画像（data URL）とテキスト層だけを送る。サーバー側の PDF ライブラリ（ネイティブ依存を伴うものが多い）を避け、デプロイと脆弱性追従の負担を増やさない。画像の縮小（長辺 2000px・JPEG 化）も同じ理由でブラウザ側で行う。

### 4. 汎用 25 列の CSV を正本にし、会計ソフト別は列写像のデータとして足す

出力の正本は**汎用 25 列**（弥生 25 項目を最大公約数に、取引先・品目・インボイス区分・税額を加えたもの。UTF-8 BOM・CRLF・`YYYY/MM/DD`・税込整数）。弥生 / freee / MF は `src/application/journal/export-presets.ts` に**列の並びをデータとして**置き、`format` を増やすだけで対応できる形にする。フェーズ 1 では列写像だけを用意し、変換は書かない（`generic` 以外は 400 で断る）。

## 検討した代替案

- **ルール照合だけ（Stage 2 無し）**: 当たらない伝票が未処理の山になる。利用者は「なぜ処理されないのか」も「何をすれば処理されるのか」も分からない。
- **毎回 LLM に仕訳を作らせる**: 同じ取引が実行ごとに違う科目になり、帳簿の一貫性が保てない。監査で説明できず、コストも件数に比例し続ける。ルールを作らせて決定的に適用する方が、回数を重ねるほど安定して安くなる。
- **勘定科目・税区分を列挙型でコードに持つ**: 型で守れる利点はあるが、科目を 1 つ足すのにコード変更と再デプロイが要る。業種差・補助科目・部門の要求に応えられない。「科目体系は固定しない」を出発点に置く。
- **ルールが科目を名前で参照する**: 改名で全ルールが壊れる。id 参照 + 確定時の名称の写しで、追従と履歴の両方を満たす。
- **サーバー側で PDF を画像化する**: ネイティブ依存とサンドボックスの手当てが増える。ブラウザには既に描画エンジンがある。
- **最初から弥生形式（または freee 形式）を正本にする**: 他社向けが全部書き直しになる。列の少ない形式を正本にすると、他形式へ写すときに情報が足りない。最大公約数 + 写像を選ぶ。

## 帰結

- Stage 1 が純粋関数なので、判定の回帰テストはモデルもデータベースも要らない。ルールの競合解決（priority → 特異度 → createdAt）もテストで固定できる。
- ルールが増えるほど LLM 呼び出しは減る。逆に、使い始めの利用者はほぼ全件が `undecided` になるので、ヒアリング（フェーズ 2）が入るまでは手でルールを作る導線が主経路になる。
- 科目マスタが利用者データなので、**マスタを壊すと既存のルールと仕訳が一斉に `unknown-account` になる**。科目 CSV の取込は勘定科目の一覧だけを置き換え、税区分と補助軸は既存のものを残す（科目 CSV に税区分の定義が無いため）。
- 科目が論理削除で残り続けるため、長く使うと無効な科目が一覧に溜まる。表示の絞り込みは UI の責務にする。
- PDF の画像化がブラウザ依存になるので、API を直接叩く利用者（スクリプト・Webhook）は自分で画像化してから送る必要がある。
- 汎用 CSV は会計ソフトへそのままは入らない（フェーズ 3 で各社形式を足すまでは、利用者が列を並べ替えるか汎用形式を受ける経路を使う）。
- SQLite のスキーマは version 5（`journal_chart` / `journal_documents` / `journal_rules` / `journal_entries` / `journal_hearings` の追加のみ。既存データはそのまま）。
- 証憑本体（画像 data URL・原文・CSV 行）は `journal_documents.record_json` に同梱する（1 件 8 MiB 上限）。別ストアへ出さない代わりに、一覧は**要約**（本体を含まない形）で返す。
