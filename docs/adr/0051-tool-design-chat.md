# ADR-0051: ツール作成画面の設計アシスタントは、グラフではなく「編集操作」を提案させ、決定的に適用して検査してから返す

- Status: Accepted
- Date: 2026-09-22
- 関連: [implementation/v47](../../implementation/v47-tool-design-chat.md)（契約の正本）/ [ADR-0046](./0046-calculate-expression-assistant.md)（式提案の「提案 → 検分 → 1 回だけ差し戻し」）/ [ADR-0047](./0047-factory-lessons-from-estat.md)（12B の機械的な書き間違いは正規化で消す）/ [ADR-0048](./0048-staged-tool-generation.md)（モデルにグラフの JSON を書かせない）/ [ADR-0049](./0049-tool-templates.md)

## 文脈

ツールを作る経路は 3 つある: 空のキャンバスに 1 つずつノードを置く / テンプレートを選んでスロットを埋める（ADR-0049）/ Agent Factory に目的から作らせる（ADR-0033・0048）。どれも「何を作りたいか」を文章で言って、その場でキャンバスが変わる経路ではない。関数電卓ノードにだけ「AIに式を書かせる」（ADR-0046）がある。

利用者が求めているのは、Claude Code や Codex のように**自由な文章で指示すると、いま見ているキャンバスにノードが増えたり設定が変わったりする**体験である。

## 決定

1. **モデルにはグラフ全体ではなく編集操作を返させる。** `add-node`（鎖への挿入つき）/ `remove-node` / `set-config` / `connect` / `disconnect` の 5 つ。人が組んだ配置と設定を壊さず、何が変わったかを一覧で見せられる。
2. **適用は純関数で、配線は関数が決める。** 「この後ろに足す」と言われたら、既存の出力エッジの付け替えまで関数が行う。モデルにエッジを書かせる場面を減らす。
3. **返す前に検査し、落ちたら 1 回だけ差し戻す。** 適用後のグラフを既存の正規化 → スキーマ伝播 → 設計時プレビューに掛ける。2 回目も落ちたらキャンバスは変えず、説明と理由だけ返す。
4. **キャンバスへは確認なしで即適用し、取り消しで戻す。** 毎回の確認ダイアログは会話の流れを止める。各ターンの適用前のグラフを画面が持ち、「この変更を取り消す」で戻せるようにする。
5. **指示文も会話も untrusted data 側に置く。** 規則とカタログだけを system に置く（ADR-0033 以来の規律）。
6. **保存はしない。** 返るのはキャンバスの状態で、保存は従来の操作。会話は永続化しない。

## 理由

- **差分で提案させると、小さなモデルでも壊しにくい。** 全体を書き直させると、触っていないノードの設定まで揺れる（ADR-0047 で実測）。
- **決定的な配線・正規化・検査は既に揃っている。** `normalizeProposedGraph`、`propagateSchemas`、設計時プレビューは Factory とテンプレートが使っているものと同じで、抜け道を作らない。
- **「提案 → 検分 → 1 回だけ差し戻し」は式提案で効いている**（ADR-0046）。往復を重ねるより、人が指示を直す方が速い。

## 検討した代替案

- **グラフ全体を返させて diff を見せる**: 12B は書き直しのたびに別の箇所を変える。配置も失われる。
- **テンプレート選択 + スロット埋めをチャットの裏で回す**（ADR-0049 の `select-template` / `fill-slots`）: 当てはまる形しか作れず、「この filter を引数にして」のような部分編集ができない。テンプレートは「最初の形を素早く置く」用途として残し、その後の編集をこのアシスタントが担う。
- **適用前に必ず確認ダイアログを出す**: 会話の流れを止める。取り消しがあれば、確認は要らない。
- **段階的生成（ADR-0048）の `ToolSpec` を経由する**: 語彙が閉じていて、Factory 向けに設計されている。チャットは任意のノードを扱う必要がある。

## 結果・影響

- ツール作成画面に「設計アシスタント」のパネルが増える。関数電卓アシスタントと同じモデルを使い、同じ条件で有効になる。
- 1 ターンあたりモデル呼び出し 1 回（差し戻しがあれば 2 回）+ 設計時プレビュー 1〜2 回。
- ノードのカタログ（種別ごとの config 契約の英文）を application 層に持つ。ノードの契約が変わったらここも直す。レジストリとの突き合わせテストで漏れを検出する。
- 非スコープ: 保存・公開の自動化、会話の永続化、チャットからのデータソース登録、細かな自動整列。
