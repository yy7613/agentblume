# ideas v2 — ノーコード体験の深掘り（二層構造）

> 元の `ideas.md`（構想の全体像）を踏まえた深掘り版。
> **優先軸**: ノーコード体験の深掘り / **利用者**: 非エンジニア入口＋上級者にコード開放（二層構造）

---

## 0. 貫く設計原則（全画面共通）

ノーコードのエージェントIDEで体験の質を決めるのは、機能の数ではなく次の5原則。

1. **プレビュー駆動 (Preview-first)**
   常にサンプルデータを見ながら組む。ノードを繋ぐ／設定を変えるたびに、出力スキーマとサンプル行を、固定サンプルまたはキャッシュから制限付きで更新する（Power Query / Azure Data Factory の体験）。書き込み処理はプレビューでは実行しない。
2. **エスケープハッチ (Escape hatch)**
   ノーコードで詰まった箇所は必ずコードに落とせる出口を用意する。二層構造の核。ただし **ノーコード→コードは一方向**（往復同期はしない）と割り切る。
3. **段階的開示 (Progressive disclosure)**
   初期は最小フォーム。温度・リトライ・モデルルーティング等の上級設定は「詳細」に畳む。非エンジニアを圧倒しない。
4. **即時バリデーション (Inline validation)**
   スキーマ不一致・未接続・必須未設定をその場で赤表示。実行前に間違いを潰す。
5. **SDK境界の分離 (SDK isolation)**
   外部SDKを利用する境界には必ずアプリケーション所有のインターフェースを定義する。ドメイン層とユースケース層は外部SDKを直接参照せず、SDK固有の型、例外、設定、ライフサイクルをアダプター内へ閉じ込める。

## 1. ETL ノードベース・ツールビルダー（ノーコードの心臓）

ツール = 「入力スキーマ → 変換 → 出力スキーマ」の検証済み実行単位。ここが最重要。

### ノードの分類
- **入力(source)**: DB / ファイル / API。加えて **エージェント引数**（画面で定義した引数が入力源になる）。
- **変換(transform)**: join, union, filter, sort, select, rename, cast, null処理, 重複排除, 置換, 文字列整形, group by集計, ウィンドウ関数, 計算列, pivot/unpivot, split/merge, 日付変換, リサンプリング（元アイデア踏襲）。
- **分析(analyze)**: 基本統計, 相関, 時系列。
- **出力(sink)**: Chart.js用グラフデータ / LLMへ渡す / ワークスペース格納 / MCP公開。
- **★制御ノード（将来のWorkflow Builder）**: 分岐(if/switch), ループ(foreach), try/catch（エラーハンドリング）。ETLのデータ変換とは実行規則が異なるため、Tool Builderへ直接混在させず、複数Toolを接続するWorkflow Builderの責務とする。
- **★カスタムコードノード（追加・エスケープハッチ）**: ノードで表現できない変換をサンドボックス内のコードで書く。二層構造の入口。実行時間・メモリ・ネットワーク・ファイルアクセスを制限できることを提供条件とする。

### ノーコードを成立させる仕掛け
- **スキーマ自動伝播**: 各ノードの出力スキーマを推論し、下流ノードの列選択をドロップダウン提示。型不一致は接続線を赤く。スキーマ状態は「確定 / 部分確定 / 推論 / 不明 / 実行結果と不一致」を区別する。
- **式エディタ（GUI + テキスト二層）**: filter条件や計算列を、GUIビルダーで組む→上級者は生の式に切替。ここが no-code / code の境界。
- **データプロファイリング（追加）**: 入力データの件数・null率・値分布・型を自動表示。変換設計の前提が一目で分かる。
- **サブフロー化（追加）**: 複雑なフローの一部を1ノードに畳んで再利用（ツールの再帰的合成）。
- **サンプル固定 & スナップショットテスト**: 代表入力を保存し、変更で出力が変わったら差分検知。
- **副作用の宣言**: read-only か 書き込みあり か（冪等性・承認要否）をメタデータ化。エージェント実行時の安全性に直結。

### I/O 契約化（検証可能な境界の具体化）
- フローの入口 = **引数スキーマ**、出口 = **出力スキーマ**。
- 引数スキーマは、LLMがToolを呼び出すための **Tool Calling用Input Schema** に変換する。
- 出力スキーマは、Tool実行後にアプリケーション側で検証する **Output Schema** とする。Zodは実装時の検証表現、JSON Schemaは保存・交換用の標準表現として扱う。
- API、pivot、カスタムコードなどで出力を推論できない場合は、作成者がOutput Schemaを明示し、実行時に実データとの一致を検証する。

## 2. スキル・コンポーザー

スキル = 責務・入力・出力・依存ツールの束（再利用単位）。

- **カードUI**: 依存ツールをドラッグで束ねる。スキルの入出力も構造化定義。
- **発火条件を自然言語で記述**: 「いつLLMがこのスキルを選ぶか」を書くと、それが後述のプロンプト自動生成に反映される。
- **スキル選択の検証**（元アイデア）とセットで、条件文の良し悪しを数値で測れる。単純な呼び出し率ではなく、期待するSkill、呼び出し要否、引数、順序、最終タスク成否をテストケースごとに定義する。

---

## 3. エージェント・アセンブラ

エージェント = システムプロンプト + 構造化出力 + Skill + Tool。

- **キャンバス/フォームで組む**: Skill・Tool をドラッグして構成。
- **★プロンプト自動生成（元アイデアの具体化・目玉機能）**:
  選んだ Skill/Tool のメタデータ（責務・入出力・発火条件）から、system prompt のスキル説明部とツール使用ガイドを**自動生成**。生成結果は必ず人がレビュー・編集できる（エスケープハッチ）。
- **★構造化出力スキーマGUIエディタ**: JSON Schema / Zod を GUI で組む。検証可能な境界の設計を非エンジニアでも。
- **横並びプレビュー・チャット**: 組みながら右ペインで即対話テスト（Chat画面統合）。
- **テンプレート/レシピ**: 空白から始めない。RAG-QA / データ分析 / 疑似ユーザー / 評価用 など構成テンプレから開始。
- **エージェント種別**（元アイデア）: 通常 / 疑似ユーザー（ユーザープロファイル駆動）/ 評価用。

## 4. 二層構造（混在対応）— エスケープハッチ設計

非エンジニアの入口を保ちつつ、上級者を天井で縛らないための出口一覧。

| レイヤ | ノーコード | エスケープハッチ（コード） |
|---|---|---|
| ETL変換 | ノード + GUI式 | 生SQL/JS式 → カスタムコードノード |
| ツール全体 | ノードフロー | Mastraツールとしてコード書き出し |
| プロンプト | 自動生成 | 手編集 |
| 出力スキーマ | GUIエディタ | Zod/JSON Schema 直書き |
| エージェント全体 | キャンバス | **Mastraコードへエクスポート** |
| トリガー | cron/イベントGUI | Webhookハンドラ記述 |

**割り切り**: エクスポートは「コードプロジェクトとして分岐」する一方向操作とする。分岐後のコードはノーコード側へ同期せず、IDE側の更新・検証・デプロイ対象から外れる。一方、カスタムコードノードはノーコードプロジェクト内の不透明な1ノードとして保存・再編集できる。

## 5. ノーコードを支える横断機能（追加）

- **テンプレートギャラリー**: ツール/スキル/エージェント/ワークフローの雛形集。
- **undo/redo・複製・コピー**: キャンバス操作の基本作法。
- **インライン・ドキュメント/ツールチップ**: 各ノード・設定の説明をその場で。
- **実行トレースの可視化（最小版）**: どのノード/どのサンプル行で落ちたかを色で示す。フル観測は元アイデアの Status画面を将来格上げ（v2以降）。
- **cron/イベントトリガーのGUI**: 定期実行・Webhookをノーコードで設定。
- **認証・認可モジュール**: ログイン画面、アカウント管理、セッション管理、権限管理を、利用するIdentity ProviderやWebフレームワークに応じて差し替えられるようにする。

## 7. 対象ユーザーとv1の代表ジャーニー

### 対象ユーザー
- **主対象**: データ加工や業務手順は理解しているが、アプリケーションコードを日常的には書かない業務担当者・アナリスト。
- **副対象**: ノーコードで開始し、必要な部分だけ式・SQL・コードへ降りたい開発者。
- **運用担当者**: 接続先、権限、公開範囲、実行履歴を管理する管理者。

### v1で完結させる一本のジャーニー
1. CSV/JSONの固定サンプルを読み込む。
2. select / filter / rename / castでデータを変換する。
3. 各ノードでサンプル行とスキーマ変化を確認する。
4. ToolのInput SchemaとOutput Schemaを確定する。
5. ToolをAgentへ接続し、横並びチャットから試す。
6. Tool選択、入力、各ノードの出力、エラーをトレースで確認する。
7. 検証済み構成をバージョン付きで保存する。

### v1の非目標
DB直接接続 / MCP外部公開 / カスタムコード実行 / Workflow制御ノード / cron / Webhook / 複数人の同時編集は、上記ジャーニーの成立後に追加する。設計上の拡張点は先に用意するが、初期リリースへ機能を詰め込まない。

## 8. 実行モデルとプレビュー規則

- **Tool Builder**: 入力から出力までの、可能な限り決定的で再実行可能なデータ変換を担当する。
- **Workflow Builder**: 複数Toolの接続、分岐、反復、再試行、承認、スケジュール実行を担当する。
- **Agent Builder**: LLMによるSkill/Toolの選択、引数生成、構造化応答を担当する。
- プレビューは固定サンプルまたは明示的に取得したキャッシュを使用し、行数、データサイズ、実行時間を制限する。
- 書き込み、副作用を伴うAPI、通知送信はプレビューで実行しない。代わりに入力と予想される操作内容を表示する。
- 外部APIは保存済みレスポンスへ切り替えられるようにし、プレビューが課金、レート制限、外部状態に依存しないようにする。
- プレビュー、テスト、本番実行を明確に表示し、使用データと権限を分離する。

### SDK境界の実装ルール

- インターフェースはアプリケーション側が必要とするユースケースを基準に定義し、外部SDKのAPIをそのまま写さない。
- Mastra、LLM Provider、MCP Client/Server、Identity Provider、Secrets、Storage、Telemetryなどの外部SDKは、対応するPortを介して利用する。
- SDKのimportはinfrastructure/adapter層に限定し、ドメイン層、ユースケース層、UI層から直接利用しない。
- SDK固有の型、例外、ストリームイベント、認証設定は、アプリケーション共通の型とエラーへ変換する。
- SDKごとの差異はCapabilityとして明示し、未対応機能を暗黙のフォールバックで処理しない。
- 実装アダプターの選択と初期化はComposition Rootへ集約し、依存性注入によって差し替える。
- 各Portには契約テストを用意し、実SDKアダプターとテスト用Fakeが同じ契約を満たすことを検証する。
- SDKのバージョン更新による修正範囲は原則としてアダプター内に限定する。共通契約の変更が必要な場合は、影響を受けるユースケースを明示してから変更する。

想定する主な境界は、`AgentRuntimePort`、`ModelProviderPort`、`McpClientPort`、`McpServerPort`、`AuthenticationProvider`、`AuthorizationProvider`、`SecretProvider`、`StoragePort`、`TelemetryPort` とする。

## 9. セキュリティ最低要件

DB/API接続、カスタムコード、MCP公開、Webhookを提供する前に、次を満たす。

- 資格情報はフロー、プロンプト、生成コードへ埋め込まず、Secrets Providerの参照として保存する。
- カスタムコードは時間、メモリ、CPU、ネットワーク、ファイルアクセス、利用可能パッケージを制限した分離環境で実行する。
- Toolは副作用を `read-only / write / external-action` として宣言し、writeとexternal-actionにはポリシーに応じて実行前承認を要求する。
- MCP、Webhook、公開Agentのエンドポイントは未認証公開を既定にしない。
- 実行者、対象バージョン、入力の参照、使用Tool、承認、結果、エラーを監査ログへ記録する。秘密情報と個人情報はマスキングする。
- ワークスペース、接続、Tool、Skill、Agent、公開エンドポイントごとにアクセス制御を適用できるようにする。

## 10. 認証・認可の差し込み設計

本製品独自のユーザー管理へ固定せず、一般的なWebアプリケーションの認証・認可機能をアダプターとして挿入できる構造にする。

### 認証（Authentication）
- OIDC / OAuth 2.0を標準の接続境界とし、Microsoft Entra ID、Auth0、Keycloak、OktaなどのIdentity Providerを差し替え可能にする。
- 小規模・ローカル利用向けに、セッション方式のローカル認証アダプターも実装可能にする。ただし、本番の既定は外部Identity Provider連携とする。
- Web UIはAuthorization Code Flow + PKCEを基本とし、APIは短寿命アクセストークンまたは安全なサーバーサイドセッションを使用する。
- Webhook、MCP、サービス間通信ではユーザー認証と分離したService Principal / Client Credentials / 署名付きトークンを利用できるようにする。
- 認証アダプターは、内部の共通Principalへ `subject / tenant / displayName / groups / claims / authenticationMethod` を正規化して渡す。
- ログイン、ログアウト、ユーザー登録、招待、メール確認、パスワード再設定、MFA/パスキー、ソーシャルログイン、セッション失効、アカウント無効化を任意機能として宣言できるCapability方式にする。外部Identity Providerが担当する機能をアプリ側で重複実装しない。
- セッションCookieを使う場合はHttpOnly、Secure、SameSite、CSRF対策、セッションIDのローテーションと失効を共通基盤で扱う。

### 認可（Authorization）
- 認証済みPrincipalに対して認可を行い、認証の有無だけで操作を許可しない。
- 初期実装はRBACとし、`Viewer / Editor / Publisher / Operator / Workspace Admin`などのロールをワークスペース単位で割り当てる。
- 判定対象は少なくとも `workspace / connection / secret-reference / tool / skill / agent / workflow / deployment / audit-log` とする。
- 判定操作は `read / create / edit / execute / approve / publish / manage-access / delete` のように分離する。
- 将来、所有者、環境、データ分類、テナント、Toolの副作用などを条件にするABAC/Policy Engineを追加できる認可インターフェースを用意する。
- UI上の非表示だけに依存せず、すべてのAPI、実行要求、公開操作でサーバー側の認可判定を行う。
- 権限が未定義、または認可プロバイダーが利用不能な場合は、既定で拒否する。

### 拡張インターフェース
- `AuthenticationProvider`: ログイン、ログアウト、コールバック、セッション/トークン検証を担当する。
- `AuthFeatureProvider`: 登録、招待、メール確認、パスワード再設定、MFA、セッション一覧など、一般的なアカウント機能の対応可否と実行方法を提供する。
- `AuthUiExtension`: ログイン、登録、アカウント、セッション、メンバー管理画面のルートとUIコンポーネントを差し替える。
- `PrincipalMapper`: Identity Provider固有のclaimを内部Principalへ変換する。
- `AuthorizationProvider`: Principal、resource、action、contextを入力として許可・拒否を返す。
- `SecretProvider`: 接続情報の参照と実行時取得を担当し、認証・認可処理と資格情報の保管を分離する。
- `AuditSink`: 認証イベント、認可拒否、承認、公開、実行を外部監査基盤へ転送可能にする。

認証・認可モジュールは、画面だけでなくHTTPミドルウェア、APIルート、サーバー側ポリシー判定、監査イベントを一つの構成単位として登録する。これにより、一般的なWebアプリの認証画面だけを挿入してAPIが無防備になる状態を防ぐ。

### テナントと権限境界
- すべての永続データにtenant/workspace境界を持たせ、問い合わせ時に必ず適用する。
- 外部Identity Providerのgroup/roleを内部ロールへマッピングできるようにする。
- 初回ログイン時のJITプロビジョニング、管理者による招待、外部ディレクトリ同期を選択可能にし、ユーザー作成経路をテナントポリシーで制御する。
- Agentが利用者の代理で外部サービスへ接続する場合は、共有資格情報、ユーザー委任、サービス資格情報を区別して表示・監査する。
- 管理者であっても秘密値そのものを標準画面から読み出せない設計を基本とする。

## 11. 検証指標

テストケースごとに期待するSkill/Tool、呼び出し要否、入力制約、順序、期待出力を定義し、次を測定する。

- 呼ぶべき場合に正しいSkill/Toolを呼んだ割合。
- 呼ぶべきでない場合に呼ばなかった割合。
- Tool引数と構造化出力のスキーマ適合率。
- 必要な呼び出し順序と承認手順の適合率。
- 最終タスク成功率、応答時間、LLMおよび外部APIの実行コスト。
- 同じ固定データセットに対する変更前後の回帰差分。

### Phase 3: 拡張実行
カスタムコードのサンドボックス、MCP公開、Webhook、Workflow Builder、cron、コードプロジェクトへの分岐。

### Phase 4: 評価と運用
データセット評価、回帰、LLM-as-Judge、本番ログからの評価データ化、環境昇格、高度なポリシー制御。
